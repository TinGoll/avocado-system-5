# Единый реестр шаблонных переменных: задачи реализации и миграции работ

## Назначение документа

Этот план описывает внедрение единого реестра переменных с контекстами использования и безопасный перевод существующих формул и шаблонов производственных работ на новый реестр.

Добавление шаблона вывода для номенклатуры в этот этап **не входит**. Архитектура должна позволять позже добавить новый контекст использования без изменения рендерера и без влияния на текущий UX номенклатуры.

## Зафиксированные архитектурные решения

### Реестр хранит описание, но не получает доменные данные

Единый реестр содержит метаданные переменной:

```ts
type TemplateVariableDefinition = {
  path: string;
  label: string;
  description: string;
  valueType: 'string' | 'number' | 'boolean';
  unit?: string;
  scopes: TemplateVariableScope[];
  optional?: boolean;
};
```

Реестр не должен импортировать `Order`, `OrderItem`, `ProductTemplate`, `ProductionOperation` и не должен содержать функции-resolver'ы, читающие доменные сущности. Доменные модули сами строят плоский или вложенный объект значений и передают его рендереру.

### Контексты использования разделяются по назначению

Для текущих работ необходимы два разных scope:

```ts
export const TEMPLATE_VARIABLE_SCOPE = {
  PRODUCTION_OPERATION_FORMULA: 'production-operation-formula',
  PRODUCTION_OPERATION_NAME: 'production-operation-name',
} as const;
```

Разделение обязательно: строковые `item.name`, `profile.name` и `panel.name` допустимы в шаблоне названия, но не в арифметической формуле.

Scope будущего продуктового вывода следует добавить только в задаче реализации продуктового шаблона. На этом этапе не создавать пустой `PRODUCT_OUTPUT` и не добавлять неиспользуемые продуктовые переменные.

### Ответственность компонентов

```text
server/src/common/template-variables/
├── template-variable-registry.ts    # определения и выборка по scope
├── template-renderer.service.ts     # разбор и рендер {{ variable }}
├── template-variables.types.ts      # общие типы
├── template-variables.module.ts     # NestJS-модуль и exports
└── *.spec.ts                        # независимые unit-тесты

server/src/modules/production-operations/
├── production-operation-calculator.service.ts
│   # арифметика, геометрия, контекст работы и адаптация ошибок
└── types/production-operation-formula-contract.ts
    # доменный контракт работы и совместимые публичные ошибки
```

Общий рендерер отвечает только за:

- поиск конструкций `{{ variable.path }}`;
- проверку доступности пути в переданном scope;
- получение значения из переданного контекста;
- ошибку неизвестной или отсутствующей переменной;
- преобразование разрешённого значения в строку;
- возврат отрендерованной строки и списка использованных переменных.

В калькуляторе работ остаются:

- парсер и вычислитель арифметических выражений;
- проверка числового типа переменной формулы;
- деление на ноль, `NaN`, бесконечность и отрицательный результат;
- построение контекста из снимка заказа;
- вычисление `panelWidth` и `panelHeight`;
- адаптация ошибок общего механизма к текущему API работ.

### Целевой поток данных

```text
OrderItem + Order characteristics
              │
              ▼
ProductionOperationCalculatorService.contextFromSnapshot()
              │
              ▼
ProductionOperationEvaluationContext
              │
       ┌──────┴────────┐
       ▼               ▼
арифметическая      TemplateRendererService
формула             scope: production-operation-name
       │               │
       └──────┬────────┘
              ▼
calculatedQuantity + renderedName
```

## TVR-01. Зафиксировать совместимость текущего поведения работ

**Цель:** создать исполняемую защиту от регрессии до извлечения общего механизма.

**Контекст:** логика парсинга шаблона и чтения переменных сейчас является private-частью [`ProductionOperationCalculatorService`](server/src/modules/production-operations/production-operation-calculator.service.ts). Существующие unit-тесты проверяют основные сценарии, но перед рефакторингом необходимо явно зафиксировать весь внешний контракт.

**Работы:**

- Дополнить тесты калькулятора характеристическими сценариями текущего поведения.
- Зафиксировать успешные сценарии:
  - пробелы внутри `{{ item.width }}`;
  - несколько и повторное использование переменных;
  - числовые и строковые значения;
  - `item.name`, `profile.name`, `panel.name` только в шаблоне;
  - вычисляемые `panelWidth` и `panelHeight`;
  - шаблон без переменных.
- Зафиксировать ошибочные сценарии:
  - неизвестная переменная;
  - известная, но отсутствующая переменная;
  - строковая переменная в формуле;
  - некорректная конструкция шаблона;
  - превышение длины;
  - поле, код, HTTP-статус и текст существующей ошибки.
- При необходимости добавить service-тест preview, подтверждающий неизменность HTTP payload.
- Не изменять production-код, кроме минимальной корректировки, если тест обнаружит уже существующее несоответствие документированному контракту; такую корректировку предварительно описать отдельно.

**Критерии приёмки:**

- Тесты описывают фактическое и документированное поведение, а не желаемый новый контракт.
- `npm test -- production-operation-calculator.service.spec.ts` в `server/` проходит.
- Если добавлен service-тест, проходит и соответствующий spec.
- В diff нет изменений БД, DTO, клиента и публичных типов результата.

**Зависимости:** нет.

## TVR-02. Реализовать общий реестр переменных

**Цель:** создать единственный источник метаданных и разрешений переменных по scope.

**Контекст:** текущие массивы `PRODUCTION_OPERATION_FORMULA_VARIABLES` и `PRODUCTION_OPERATION_TEMPLATE_VARIABLES` находятся в [`production-operation-formula-contract.ts`](server/src/modules/production-operations/types/production-operation-formula-contract.ts), а описания для пользователя отдельно продублированы на клиенте в [`ProductionOperationEditorFields.tsx`](client/src/features/create-production-operation/ui/ProductionOperationEditorFields.tsx).

**Работы:**

- Создать общий каталог `server/src/common/template-variables/` согласно архитектуре выше.
- Добавить тип scope и тип определения переменной.
- Перенести в реестр текущие переменные работ без переименования путей.
- Для каждой переменной указать тип, понятное русское описание, единицу измерения и допустимые scopes.
- Реализовать API реестра:
  - получить определения по scope;
  - получить определение по `path + scope`;
  - проверить доступность переменной;
  - вернуть контролируемую ошибку для неизвестного scope при внутреннем использовании.
- Гарантировать уникальность `path` внутри каждого scope тестом или проверкой при инициализации.
- Не удалять старые экспортируемые массивы из production-operations в этой задаче. Временно построить их из реестра либо оставить совместимый адаптер, чтобы переход был поэтапным.

**Критерии приёмки:**

- В реестре ровно тот же набор путей, который сейчас поддерживают работы.
- `item.name`, `profile.name`, `panel.name` отсутствуют в scope формулы и присутствуют в scope названия.
- Все переменные арифметической формулы имеют `valueType: 'number'`.
- Unit-тесты проверяют фильтрацию по scope, уникальность и поиск неизвестного пути.
- Тесты TVR-01 продолжают проходить без изменения ожиданий.

**Зависимости:** [TVR-01](#tvr-01-зафиксировать-совместимость-текущего-поведения-работ).

## TVR-03. Реализовать общий рендерер строковых шаблонов

**Цель:** вынести универсальную обработку `{{ variable }}` из калькулятора работ.

**Контекст:** общий рендерер должен быть применим к будущим контекстам, но на этом этапе реализуется только функциональность, уже необходимая работам. Нельзя переносить в `common` арифметику или знание производственной геометрии.

**Предлагаемый интерфейс:**

```ts
type RenderTemplateOptions = {
  scope: TemplateVariableScope;
  template: string;
  values: unknown;
};

type RenderTemplateResult = {
  value: string;
  usedVariables: string[];
};
```

**Работы:**

- Реализовать `TemplateRendererService` с constructor injection реестра.
- Поддержать текущий синтаксис `{{ path }}` и пробелы вокруг пути.
- Валидировать каждую переменную через реестр и переданный scope.
- Читать только явно разрешённые пути. Не разрешать произвольный обход прототипа, `__proto__`, `constructor`, индексы массивов и пути, отсутствующие в реестре.
- Различать неизвестную переменную и отсутствующее значение известной переменной.
- Не использовать `eval`, `new Function` или выполнение пользовательского кода.
- Ввести внутреннюю типизированную ошибку общего рендерера. Не связывать её с полем `displayNameTemplate`: отображение на доменное поле выполняет вызывающий модуль.
- Добавить независимые unit-тесты, повторяющие шаблонные сценарии TVR-01.
- Не подключать сервис к производственным работам в этой задаче.

**Критерии приёмки:**

- Рендерер не импортирует файлы из `modules/production-operations`, `orders`, `products` или `pricing`.
- Результаты успешного рендера совпадают с текущим калькулятором работ.
- Ошибки содержат машинный код и имя переменной, но не раскрывают stack trace в HTTP самостоятельно.
- Тесты защищают от доступа к неразрешённым и прототипным путям.
- Все проверки TVR-01 и TVR-02 проходят.

**Зависимости:** [TVR-02](#tvr-02-реализовать-общий-реестр-переменных).

- Полный `npm test` в `server/` проходит.
- Preview работы возвращает прежний JSON.
- Сохранённые работы и `productionOperationResults` не требуют миграции.
- Внешние потребители калькулятора не изменены либо изменения ограничены настройкой DI.
- В калькуляторе больше нет собственной реализации подстановки `{{ variable }}`.

## TVR-05. Перевести валидацию переменных формулы работ на реестр

**Цель:** сделать реестр единым источником разрешений как для шаблона названия, так и для арифметической формулы.

**Контекст:** синтаксический разбор и вычисление арифметики остаются внутри калькулятора работ. Реестр заменяет только локальный whitelist и предоставляет метаданные типа.

**Работы:**

- При разборе идентификатора формулы проверять его через scope `PRODUCTION_OPERATION_FORMULA`.
- Дополнительно проверять `valueType === 'number'` перед вычислением.
- Сохранить текущий AST и арифметический evaluator без обобщения на другие домены.
- Сохранить текущие доменные ошибки `UNKNOWN_VARIABLE`, `MISSING_VALUE` и `INVALID_SYNTAX`.
- Удалить оставшийся локальный whitelist формульных переменных после проверки отсутствия импортов.
- Обновить [`FORMULA_CONTRACT.md`](server/src/modules/production-operations/FORMULA_CONTRACT.md): указать, что перечень переменных задаётся центральным реестром, но семантика формулы не изменилась.

**Критерии приёмки:**

- Набор допустимых формул не расширился и не сократился.
- Строковые переменные по-прежнему нельзя использовать в формуле.
- Все тесты калькулятора, pricing и preview проходят без изменения бизнес-ожиданий.
- В модуле работ нет отдельного массива, являющегося вторым источником разрешённых путей.

**Зависимости:** [TVR-04](#tvr-04-перевести-шаблон-названия-работ-на-общий-реестр-и-рендерер).

## TVR-06. Добавить серверный API метаданных переменных

**Цель:** убрать ручное дублирование описаний переменных на клиенте.

**Контекст:** сейчас клиентский редактор содержит статический массив путей и описаний. API должен раскрывать только безопасные UI-метаданные реестра, без функций разрешения, внутренних классов и значений реального заказа.

**Предлагаемый API:**

```http
GET /template-variables?scope=production-operation-name
GET /template-variables?scope=production-operation-formula
```

Пример ответа:

```json
{
  "variables": [
    {
      "path": "item.width",
      "label": "Ширина позиции",
      "description": "Ширина позиции заказа",
      "valueType": "number",
      "unit": "мм",
      "optional": true
    }
  ]
}
```

**Работы:**

- Добавить controller общего модуля или отдельный read-only controller рядом с ним.
- Валидировать query `scope` через DTO/pipe и возвращать 400 для неизвестного scope.
- Возвращать стабильный порядок переменных.
- Не возвращать поля, предназначенные только для внутренней реализации.
- Добавить controller/e2e-тесты для обоих scope и неизвестного значения.
- Не менять существующие endpoints `/production-operations` и `/production-operations/preview`.

**Критерии приёмки:**

- Клиент может получить полный список без локального знания серверного контракта.
- Scope формулы не содержит строковых переменных.
- API не возвращает значения заказов и не позволяет запросить произвольный путь.
- Серверные тесты и production build проходят.

**Зависимости:** [TVR-05](#tvr-05-перевести-валидацию-переменных-формулы-работ-на-реестр).

## TVR-08. Финальная проверка совместимости и очистка переходных адаптеров

**Цель:** завершить миграцию и убедиться, что реестр стал единственным источником переменных работ.

**Работы:**

- Найти через `rg` все списки путей `item.*`, `profile.*`, `panel.*`, `panelWidth`, `panelHeight`.
- Удалить временные deprecated-алиасы, если внешних потребителей больше нет.
- Проверить, что документация, API и UI получают список из одного реестра.
- Выполнить серверные unit/e2e-тесты, клиентские тесты и production build обоих пакетов.
- Вручную проверить сценарий preview:
  - формула `panelWidth / 1000 * panelHeight / 1000 * item.quantity`;
  - шаблон `{{ item.name }}: {{ panelHeight }}х{{ panelWidth }} — {{ item.quantity }} шт.`;
  - размеры `500×860`, профиль `50`, паз `10`, количество `1`;
  - ожидаемая внутренняя геометрия `420×780`.
- Проверить неизвестную переменную отдельно в формуле и шаблоне.
- Зафиксировать в итоговом отчёте команды проверки и подтверждение отсутствия миграций БД.

**Критерии приёмки:**

- Реестр является единственным источником разрешённых переменных и UI-метаданных работ.
- Поведение существующих работ и сохранённых результатов не изменилось.
- Изменений схемы БД и миграций нет.
- Все проверки проходят; предупреждения, существовавшие до изменений, отдельно отмечены и не маскируются.

**Зависимости:** [TVR-07](#tvr-07-перевести-редактор-работ-на-серверные-метаданные).

## Рекомендуемый порядок выполнения

```text
TVR-01 → TVR-02 → TVR-03 → TVR-04 → TVR-05 → TVR-06 → TVR-07 → TVR-08
 тесты     реестр   рендерер   шаблоны    формулы     API       клиент    аудит
```

TVR-01 — TVR-05 желательно выполнять последовательно: это позволяет в каждом коммите сохранять рабочее состояние и отдельно проверить совместимость. TVR-06 и TVR-07 также лучше разделить на серверный и клиентский коммиты.

## Что явно не входит в эти задачи

- поле шаблона у `ProductTemplate`;
- рендер результата продукта;
- изменение `snapshot.name` или существующих названий в UX;
- миграции базы данных;
- пользовательские форматтеры, условия и функции в шаблонах;
- произвольные пути дополнительных характеристик;
- переписывание арифметического парсера работ;
- изменение жизненного цикла перерасчёта заказов.

После завершения TVR-08 продуктовый шаблон сможет подключиться отдельной серией задач: добавить новый scope, определения переменных и доменный сборщик контекста, не меняя общий рендерер и существующие scopes работ.
