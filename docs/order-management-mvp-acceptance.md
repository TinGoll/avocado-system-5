# Приёмка MVP управления заказами (OM-12)

Дата проверки: 15 сентября 2026 года.

## Автоматизированные сценарии

Сквозной SQLite-сценарий находится в `server/test/order-management-mvp.e2e-spec.ts`. Он проверяет:

- создание custom status, доски и двух карточек одного заказа;
- запуск заказа, перенос документов на этапы 50% и 100%, средний прогресс 75% и наследование календарного срока;
- создание правила, событие перехода, единственное сохранённое уведомление после двух проходов scheduler и сохранение `readAt`;
- копирование документа без срока, custom status и карточки (после копии сводка становится 50% для трёх документов);
- архивирование назначенного статуса, запрет его удаления и запрет архивирования доски с незавершённой карточкой;
- явное закрытие без полного учёта с причиной, запрет перемещения terminal-заказа, возобновление, отмену и повторное возобновление;
- удаление группы с сохранением снимков истории и завершённого уведомления;
- конкурентный повтор одного переноса: один ответ 201, один 409, одно событие `stage_changed`;
- нагрузочный набор 10 000 документов, 100 включённых правил и 200 карточек с двумя cursor-страницами.

Приёмка дополняет существующие тесты `order-management.e2e-spec.ts`, `production-boards.e2e-spec.ts`, `database-sqlite.e2e-spec.ts` и клиентские тесты маршрутов, уведомлений, localStorage-синхронизации и HashRouter/BrowserRouter.

## Исправленный дефект

В SQLite `occurredAt` события создаётся с секундной точностью, а `activatedAt` правила ранее сохранялся с миллисекундами. Событие, возникшее сразу после создания или изменения правила в ту же секунду, ошибочно считалось более старым и пропускалось. Теперь сохраняемая граница активации округляется вниз до начала секунды. Сквозной тест создаёт правило непосредственно перед переносом документа и защищает этот случай от регрессии.

## Производительность

Окружение: Windows 10 Home 10.0.19045, Intel Core i7-3770 (4 ядра / 8 потоков), 16 ГБ RAM, Node.js 24.14.1, npm 11.11.0, SQLite `better-sqlite3` 12.11.1. База и приложение выполнялись локально, набор создавался в одноразовой SQLite БД.

Результат контрольного запуска:

| Операция | Результат | Критерий |
| --- | ---: | ---: |
| Scheduler: 10 000 документов, 100 правил | 42 633,3 мс | меньше 300 000 мс |
| Первая cursor-страница, 100 из 200 карточек | 20,1 мс | меньше 500 мс |
| Вторая cursor-страница, 100 из 200 карточек | 14,8 мс | меньше 500 мс |

Это локальное измерение SQLite, не гарантия производительности production PostgreSQL. Тест выводит свежие значения при каждом запуске.

## Команды проверки и запуска

Из корня репозитория:

```powershell
npm run setup
docker compose up -d postgres
npm --prefix server run migration:run:postgres
npm run dev
```

Для SQLite задайте отдельный путь к копии БД, затем примените миграции:

```powershell
$env:DB_TYPE = 'sqlite'
$env:DB_PATH = 'C:\path\to\avocado-copy.sqlite'
npm --prefix server run migration:run:sqlite
```

Перед миграцией web-установки нужен штатный backup PostgreSQL. Перед desktop-обновлением скопируйте файл SQLite из каталога `userData` при закрытом приложении. Не запускайте destructive down-миграции на пользовательской БД.

Проверки OM-12:

```powershell
npx --prefix server jest --config test/jest-order-management-mvp.config.cjs --runInBand --coverage
npm --prefix server run test:e2e -- --runInBand
npm --prefix client run coverage
npm --prefix client run fsd:check
npm run build:all
npm run package:desktop
```

Scheduler включён по умолчанию и запускается после готовности приложения и раз в пять минут. На дополнительных репликах его необходимо отключать через `NOTIFICATIONS_SCHEDULER_ENABLED=false`. Клиент опрашивает ленту раз в две минуты только в активном окне. Примеры правил остаются выключенными до явного действия пользователя.

## Непроверенные и известные ограничения

- PostgreSQL и Docker отсутствуют в текущем окружении. Фактическое обновление копии старой PostgreSQL БД, свежая установка, транзакционная конкуренция и нагрузка PostgreSQL не проверены.
- Полный серверный e2e запускается, но два ожидания соседнего `production-operations.e2e-spec.ts` рассинхронизированы с текущим контрактом (label `Название` вместо `Название продукта` и форма ответа update item). Все 49 остальных e2e-тестов прошли до этого сбоя.
- Полный client coverage выполнил 109 из 110 тестов; один тест `CreateForm.test.tsx` превысил общий таймаут 5 секунд под параллельной нагрузкой. Отдельный повтор с увеличенным таймаутом фиксируется в результатах запуска.
- `npm run fsd:check` сообщает существовавшее ранее нарушение `src/app/ui` (`fsd/no-ui-in-app`). OM-12 новых FSD-нарушений не добавляет.
- `npm run package:desktop` первоначально остановился на локальной TLS-цепочке Forge. Повтор `$env:NODE_OPTIONS='--use-system-ca'; npx electron-forge package` из `desktop/` успешно создал `desktop/out/Avocado 5-win32-x64/Avocado 5.exe`. Пакет запустился, создал основной/GPU/network процессы и после закрытия не оставил процессов из каталога пакета. Windows UI automation для содержимого Electron в этом окружении недоступна, поэтому фактические дата и переход по HashRouter визуально не подтверждены; их покрывают сборка и клиентские route/link-тесты, но это не заменяет ручной smoke-test экрана.

Шесть решений MVP сохранены: карточка соответствует одному документу и этапу; прогресс невзвешенный; срок — календарная дата `Europe/Moscow`; уведомления общие для установки с интервалами 5/2 минуты; закрытый Electron не имеет фоновой службы; закрытие заказа явное и допускает причину неполного учёта.
