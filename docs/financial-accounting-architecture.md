# Финансовый учет: начисления, оплаты и распределение по заказам

Дата: 22 сентября 2026. Статус: архитектура и продуктовые решения согласованы; документ подготовлен для реализации. Код приложения в рамках подготовки этого документа не изменяется.

План реализации: [задачи для AI-агента с зависимостями и критериями готовности](financial-accounting-tasks.md).

Документ описывает управленческий учет взаиморасчетов с заказчиками применительно к текущему репозиторию. Это не бухгалтерский учет с планом счетов и двойной записью. Цель первой версии — в любой момент ответить на четыре вопроса:

1. Сколько начислено заказчику и за что.
2. Сколько заказчик оплатил и каким способом.
3. На какие заказы или услуги распределена каждая оплата.
4. Каков долг или нераспределенный аванс заказчика в целом и по каждому заказу.

## 1. Предлагаемое решение

Добавить отдельный домен `finance`, состоящий из трех основных понятий:

- **Начисление** — требование оплатить заказ или другую услугу.
- **Оплата** — фактически полученная от заказчика сумма.
- **Распределение** — часть оплаты, отнесенная на конкретное начисление.

Оплата не должна напрямую принадлежать только одному заказу. Одна оплата может быть распределена между несколькими начислениями, а одно начисление может быть погашено несколькими оплатами. Это дает требуемую связь «многие ко многим» и поддерживает оба сценария:

- заказчик вносит отдельный аванс по каждому заказу;
- заказчик вносит одну сумму, которую менеджер распределяет между несколькими заказами сейчас или позднее.

Остаток оплаты, еще не распределенный по начислениям, считается авансом заказчика. Он не уменьшает долг конкретного заказа, пока менеджер явно не выполнит распределение.

Начисление по заказу создается на уровне `OrderGroup`. В текущей терминологии проекта `OrderGroup` — это пользовательский заказ, а вложенные `Order` — документы заказа. Сумма заказа для начисления равна сумме `Order.totalPrice` всех его документов.

Начисление по заказу предлагается **проводить явным действием** «Создать начисление» после расчета заказа. Не следует автоматически переписывать сумму начисления при каждом редактировании позиций: это меняло бы уже сформированные отчеты задним числом. Если рассчитанная стоимость заказа изменилась после проведения, менеджер создает корректировку на разницу. Интерфейс рассчитывает эту разницу автоматически.

## 2. Что уже есть в проекте

| Область | Текущее состояние и следствие для реализации |
| --- | --- |
| Заказ | `OrderGroup` является заказом верхнего уровня, содержит `orderNumber`, заказчика, статус и документы |
| Документ заказа | `Order` содержит рассчитанную `totalPrice`; общая сумма заказа сейчас отдельно не хранится |
| Заказчик заказа | В `OrderGroup.customer` хранится JSON-снимок заказчика, а не внешний ключ на `customers` |
| Справочник заказчиков | `Customer.id` — UUID; удаление сейчас физическое |
| Цена | Денежные поля заказов хранятся как `decimal(..., 2)` и на сервере преобразуются в `number` |
| Backend | NestJS 11, TypeORM, глобальная валидация DTO, общий формат ошибок и `WrapItemsInterceptor` |
| Базы данных | Поддерживаются PostgreSQL и SQLite; для каждой схемы создаются отдельные миграции; `synchronize: false` |
| Транзакции | Есть `runDatabaseTransaction`, сериализующий конкурентные записи SQLite |
| Client | React 19, Ant Design, Emotion, SWR, Feature-Sliced Design |
| Экспорт | На клиенте уже установлен `@protobi/exceljs`, используемый для XLSX |
| Пользователи и роли | Авторизации, пользователей и ролевой модели в приложении сейчас нет |

Главное ограничение текущей модели — отсутствие надежной связи заказа со строкой справочника заказчиков. JSON-снимок полезен для истории отображения, но его нельзя использовать как единственный идентификатор финансового счета.

## 4. Термины и расчетные правила

### 4.1. Финансовый счет заказчика

Отдельная таблица счета не требуется: идентификатором счета служит `Customer.id`, а состояние рассчитывается из финансовых операций этого заказчика.

Для выбранного заказчика:

```text
начислено = сумма всех действующих операций начисления
оплачено = сумма всех неаннулированных оплат
сальдо = начислено - оплачено
долг = max(сальдо, 0)
аванс = max(-сальдо, 0)
нераспределенный аванс = сумма оплат - сумма активных распределений
```

Положительное сальдо означает долг заказчика, отрицательное — общий аванс. Распределение не участвует повторно в формуле общего сальдо: оно только объясняет, какой заказ погашен оплатой.

### 4.2. Состояние начисления или заказа

```text
сумма начисления = сумма его первоначальной операции и корректировок
оплачено по начислению = сумма активных распределений на него
остаток = сумма начисления - оплачено по начислению
```

Состояния для отображения вычисляются, а не сохраняются отдельным enum:

- `unpaid` — распределено 0;
- `partially_paid` — распределено больше 0, но меньше суммы начисления;
- `paid` — распределено ровно на сумму начисления;
- `cancelled` — начисление аннулировано.

Переплата конкретного начисления в MVP запрещена. Лишняя сумма остается нераспределенным авансом заказчика и может быть направлена на другое начисление.

### 4.3. Денежная точность

Для нового финансового домена деньги хранятся в целых копейках в поле `amountMinor` типа `bigint`. На входе API рублевая сумма валидируется как значение не более чем с двумя знаками после запятой и один раз преобразуется в копейки. Оплаты и первоначальные начисления обязаны быть положительными; знак разрешен только у корректировок. На клиенте копейки форматируются в рубли.

Это исключает накопление ошибок IEEE 754 при суммировании распределений. Сервер ограничивает значение диапазоном безопасного целого JavaScript и использует единый TypeORM transformer для PostgreSQL `bigint` и SQLite `integer`.

Существующий `Order.totalPrice` остается без изменения. При создании начисления сумма заказа нормализуется в копейки с единым правилом округления до двух знаков.

### 4.4. Даты

- `effectiveDate` начисления — дата признания начисления, календарная дата без времени.
- `paymentDate` — дата фактического получения оплаты, календарная дата без времени.
- `cancellationDate` оплаты — календарная дата сторнирования ошибочной оплаты.
- `createdAt`, `cancelledAt`, `releasedAt` — технические временные метки UTC.

Отчеты за период фильтруют начисления по `effectiveDate`, а оплаты по `paymentDate`. Аннулированная оплата отражается отдельной отрицательной строкой на `cancellationDate`, поэтому закрытый прошлый период не переписывается. Границы периода включаются. Техническое время создания не должно менять принадлежность операции отчетному дню.

## 5. Пользовательские сценарии

### 5.1. Оплата конкретного заказа

1. Менеджер открывает рассчитанный заказ.
2. Если начисления еще нет, нажимает «Создать начисление». Система показывает сумму всех документов и заказчика.
3. Менеджер выбирает «Добавить оплату».
4. Форма уже содержит заказчика и начисление этого заказа; менеджер указывает дату, способ и сумму.
5. В одной транзакции создаются оплата и распределение на заказ. Если сумма оплаты больше остатка заказа, на заказ относится только допустимая сумма, а остаток остается авансом после явного подтверждения пользователем.

### 5.2. Единая оплата на несколько заказов

1. На странице финансов менеджер создает оплату и выбирает заказчика.
2. После ввода суммы система показывает открытые начисления этого заказчика.
3. Менеджер указывает суммы напротив нужных начислений.
4. Система проверяет, что сумма распределений не превышает оплату и остатки начислений.
5. Нераспределенная часть отображается как аванс и может быть распределена позже.

### 5.3. Несколько оплат одного заказа

Каждая полученная сумма регистрируется отдельной оплатой. Для одного начисления может существовать любое количество активных распределений от разных оплат. Карточка заказа показывает начислено, оплачено и остаток.

### 5.4. Аванс до расчета заказа

Оплата может быть создана только на заказчика, без начисления и заказа. После проведения начисления менеджер открывает нераспределенные оплаты заказчика и относит нужную сумму на заказ.

### 5.5. Ручное начисление за услугу

Менеджер создает начисление с источником `manual`, выбирает заказчика, вводит название услуги, дату, сумму и комментарий. Такое начисление участвует в распределении и отчетах наравне с заказом, но не связано с `OrderGroup`.

Отдельный каталог услуг для MVP не нужен: название фиксируется текстовым снимком в начислении.

### 5.6. Изменение цены заказа после проведения

На финансовой карточке заказа одновременно показываются:

- текущая рассчитанная сумма заказа;
- проведенная сумма начисления;
- разница.

Если разница не равна нулю, менеджер выбирает «Обновить начисление». Сервер повторно читает актуальную сумму заказа и создает неизменяемую корректировку на разницу. Клиент не передает доверенную новую итоговую сумму.

Уменьшение запрещено, если после корректировки сумма начисления станет меньше уже распределенной оплаты. Сначала менеджер освобождает лишнее распределение, после чего оно возвращается в нераспределенный аванс.

### 5.7. Ошибка в оплате или начислении

Проведенные суммы не редактируются и не удаляются физически.

- Ошибочная оплата аннулируется с обязательной причиной. Ее активные распределения освобождаются в той же транзакции.
- Ошибочное ручное начисление аннулируется обратной операцией. Если на него распределена оплата, сначала необходимо освободить распределение.
- Ошибка в сумме заказа исправляется корректировкой начисления после исправления самого заказа.

Так история остается проверяемой, а повторное использование удаленных идентификаторов невозможно.

## 6. Связь заказа с заказчиком

В `order_groups` нужно добавить nullable-поле `customerId` с внешним ключом на `customers.id` и индексом. Существующее поле `customer` сохранить как снимок имени и реквизитов: оно продолжит обеспечивать историческое отображение, даже если карточка заказчика позже изменится.

Правила:

- при создании или смене заказчика API принимает `customerId`, сервер загружает `Customer` и сам формирует JSON-снимок;
- клиент больше не отправляет произвольный объект заказчика как доверенный источник связи;
- финансовое начисление по заказу разрешено только при наличии действующего `customerId`;
- после первого начисления смена `customerId` заказа запрещена; ошибочную связь исправляют аннулированием финансовых операций и явным повторным проведением;
- удаление заказчика блокируется, если на него ссылаются заказы или финансовые записи;
- удаление заказа блокируется, если для него уже создано начисление; обычная отмена заказа не аннулирует долг автоматически.

Миграция сначала добавляет nullable FK и пытается восстановить связь по `order_groups.customer.id`, если это валидный UUID существующего заказчика. Заказы без однозначной связи попадают в отдельный список «Требуется указать заказчика». Не следует угадывать связь по имени: имена могут изменяться и не являются надежным ключом.

После исправления старых данных поле можно сделать обязательным для новых заказов на уровне DTO, но не обязательно сразу делать `NOT NULL` в БД: текущий продукт допускает создание заказа без заказчика.

## 7. Модель данных

### 7.1. `financial_accruals`

Логический объект начисления и цель распределения оплаты.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | uuid PK | Идентификатор начисления |
| `customerId` | uuid FK, not null | Счет заказчика |
| `sourceType` | text | `order` или `manual` |
| `orderGroupId` | integer FK, nullable | Заказ для источника `order` |
| `title` | text | Снимок названия: номер заказа или название услуги |
| `status` | text | `active` или `cancelled` |
| `version` | integer | Оптимистическая блокировка |
| `createdAt` | timestamp | Время создания |
| `cancelledAt` | timestamp, nullable | Время аннулирования |
| `cancellationReason` | text, nullable | Причина аннулирования |

Ограничения:

- для `sourceType = order` поле `orderGroupId` обязательно;
- для `sourceType = manual` поле `orderGroupId` должно быть `null`;
- один заказ имеет не более одного `financial_accruals`;
- `customerId` начисления по заказу совпадает с `OrderGroup.customerId`;
- FK на заказ использует `ON DELETE RESTRICT`, FK на заказчика — `ON DELETE RESTRICT`.

### 7.2. `financial_accrual_entries`

Неизменяемые операции, образующие сумму начисления.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | uuid PK | Идентификатор операции |
| `accrualId` | uuid FK, not null | Родительское начисление |
| `kind` | text | `initial`, `adjustment`, `reversal` |
| `amountMinor` | bigint | Знаковая сумма в копейках, не равная нулю |
| `effectiveDate` | date | Дата попадания в отчет |
| `reason` | text, nullable | Причина корректировки |
| `reversesEntryId` | uuid FK, nullable, unique | Какая операция сторнирована |
| `requestId` | uuid, unique | Защита от повторной отправки |
| `createdAt` | timestamp | Техническое время создания |

Первоначальная операция положительная. Корректировка может быть положительной или отрицательной. Аннулирование создает `reversal`, равный отрицательной текущей сумме начисления, и меняет статус родителя на `cancelled` в одной транзакции.

Операции не обновляются и не удаляются. Сумма начисления всегда равна `SUM(amountMinor)`.

### 7.3. `financial_payments`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | uuid PK | Идентификатор оплаты |
| `customerId` | uuid FK, not null | На чей счет поступили деньги |
| `amountMinor` | bigint, positive | Полученная сумма в копейках |
| `paymentDate` | date | Дата оплаты |
| `method` | text | `cash`, `card`, `bank_transfer`, `other` |
| `externalReference` | text, nullable | Номер чека, банковской операции или документа |
| `comment` | text, nullable | Комментарий менеджера |
| `status` | text | `posted` или `cancelled` |
| `version` | integer | Оптимистическая блокировка распределений |
| `requestId` | uuid, unique | Идемпотентность создания |
| `createdAt` | timestamp | Время регистрации |
| `cancelledAt` | timestamp, nullable | Время аннулирования |
| `cancellationDate` | date, nullable | Дата отрицательной строки в отчете |
| `cancellationReason` | text, nullable | Обязательная причина |

Сумма, заказчик и дата проведенной оплаты не редактируются. Исправление выполняется аннулированием и созданием новой оплаты. При расчете оборотов аннулирование дает отрицательную сумму на `cancellationDate`; текущий итог такой оплаты равен нулю, но обе строки остаются видны в акте взаиморасчетов.

### 7.4. `financial_payment_allocations`

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | uuid PK | Идентификатор распределения |
| `paymentId` | uuid FK, not null | Оплата |
| `accrualId` | uuid FK, not null | Начисление |
| `amountMinor` | bigint, positive | Распределенная сумма |
| `status` | text | `active` или `released` |
| `createdAt` | timestamp | Время распределения |
| `releasedAt` | timestamp, nullable | Время освобождения |
| `releaseReason` | text, nullable | Причина перераспределения/аннулирования |

Изменение распределения не перезаписывает старую строку: предыдущая строка переводится в `released`, новая создается как `active`. Это дает достаточную историю без отдельной универсальной таблицы событий.

Сервис в транзакции проверяет:

- оплату и начисление одного заказчика;
- оба объекта не аннулированы;
- сумма активных распределений оплаты не превышает сумму оплаты;
- сумма активных распределений начисления не превышает его текущую сумму;
- уменьшение начисления не создает переплату;
- конкурентное изменение не прошло с устаревшей `version`.

### 7.5. Индексы

Минимально нужны:

- `financial_accruals(customerId, status, createdAt, id)`;
- unique на `financial_accruals(orderGroupId)` при ненулевом значении;
- `financial_accrual_entries(accrualId, effectiveDate, id)`;
- `financial_accrual_entries(effectiveDate, id)` для общего отчета;
- `financial_payments(customerId, paymentDate, id)`;
- `financial_payments(paymentDate, id)`;
- `financial_payments(method, paymentDate, id)`;
- `financial_payment_allocations(paymentId, status)`;
- `financial_payment_allocations(accrualId, status)`;
- unique `requestId` у создаваемых денежных операций.

Конкретные определения индексов должны быть эквивалентны в PostgreSQL и SQLite. Если частичный unique усложняет переносимость, уникальность активной пары распределения обеспечивается сервисом под блокировкой; корректность сумм от этого не зависит.

## 8. Серверная архитектура

Добавить `server/src/modules/finance/` как отдельный feature-модуль:

```text
finance/
  dto/
  entities/
  finance.module.ts
  finance.controller.ts
  finance-accruals.service.ts
  finance-payments.service.ts
  finance-allocations.service.ts
  finance-reports.service.ts
  finance-money.ts
```

Ответственность разделяется, чтобы не создавать один большой сервис:

- `FinanceAccrualsService` проводит заказ, создает ручное начисление, корректировку и аннулирование;
- `FinancePaymentsService` регистрирует и аннулирует оплаты;
- `FinanceAllocationsService` атомарно заменяет распределение оплаты;
- `FinanceReportsService` выполняет агрегирующие запросы и строит read-модели отчетов;
- `finance-money.ts` содержит только правила преобразования и проверки денежных величин домена finance.

Все команды, меняющие несколько строк или проверяющие суммы, выполняются через `runDatabaseTransaction`. В PostgreSQL изменяемые оплаты и начисления блокируются на время проверки. В SQLite записи проходят через существующую сериализацию транзакций.

Модуль finance может читать `Customer`, `OrderGroup` и `Order` через зарегистрированные TypeORM repositories. `OrdersModule` не должен импортировать `FinanceModule`: явная команда проведения вызывается через finance endpoint, поэтому циклическая зависимость не требуется.

DTO валидируют enum, UUID, даты, длину текста, диапазон суммы и `expectedVersion`. Бизнес-ошибки возвращаются в существующем формате проекта:

- `400` — некорректная сумма, дата или состав распределения;
- `404` — заказчик, заказ, начисление или оплата не найдены;
- `409` — устаревшая версия, превышение доступной суммы, несовпадение заказчика или повторное проведение заказа;
- `422` — команда синтаксически верна, но нарушает финансовое состояние, например уменьшает начисление ниже уже оплаченной суммы.

### Идемпотентность

Клиент генерирует UUID `requestId` для создания оплаты и каждой операции начисления. Повтор запроса с тем же `requestId` и теми же данными возвращает ранее созданный результат. Повтор с иным содержимым возвращает `409`. Это защищает от двойной оплаты при повторном нажатии или восстановлении сети.

## 9. HTTP API

Все пути имеют существующий префикс `/api`. Списки с метаданными возвращаются как `{ items, meta }`, чтобы `WrapItemsInterceptor` не оборачивал их повторно.

| Endpoint | Назначение |
| --- | --- |
| `GET /finance/summary` | Общая сводка: начислено, оплачено, долг, аванс, нераспределено |
| `GET /finance/customers/:customerId` | Сводка и последние операции заказчика |
| `GET /finance/customers/:customerId/statement` | Акт взаиморасчетов за период |
| `GET /finance/order-groups/:orderGroupId` | Финансовое состояние заказа и отличие от текущей рассчитанной цены |
| `GET /finance/accruals` | Начисления с фильтрами и пагинацией |
| `POST /finance/accruals/manual` | Ручное начисление |
| `POST /finance/accruals/from-order` | Первичное проведение рассчитанного заказа |
| `POST /finance/accruals/:id/sync-order-total` | Корректировка до актуальной суммы заказа |
| `POST /finance/accruals/:id/adjustments` | Ручная корректировка с причиной |
| `POST /finance/accruals/:id/cancel` | Аннулирование начисления |
| `GET /finance/payments` | Оплаты с фильтрами и пагинацией |
| `POST /finance/payments` | Создание оплаты, опционально вместе с распределениями |
| `GET /finance/payments/:id` | Оплата, активные и освобожденные распределения |
| `PUT /finance/payments/:id/allocations` | Атомарная замена активного распределения по полной карте |
| `POST /finance/payments/:id/cancel` | Аннулирование оплаты и освобождение распределений |
| `GET /finance/reports/turnover` | Данные отчета по начислениям и оплатам за период |

Основные фильтры списков и отчетов:

- `dateFrom`, `dateTo`;
- `customerId`;
- `sourceType` для начислений;
- `method` для оплат;
- `status`;
- `allocationState=unallocated|partial|allocated`;
- поиск по номеру заказа, названию услуги, заказчику, комментарию и внешнему номеру.

Пагинация использует стабильный cursor по паре `(businessDate, id)`, где `businessDate` — `effectiveDate` или `paymentDate`. Сортировка по умолчанию — сначала новые даты, затем `id`.

Пример создания одной оплаты с распределением:

```json
{
  "requestId": "1b545999-833f-4850-b889-96d8288e05e3",
  "customerId": "d0ebee7c-1a83-4b3b-a9f5-c92b8230748a",
  "amount": "150000.00",
  "paymentDate": "2026-09-22",
  "method": "bank_transfer",
  "externalReference": "Платежное поручение 154",
  "comment": "Оплата по двум заказам",
  "allocations": [
    { "accrualId": "e2981d2d-60a8-4d43-92fa-234321a99cc4", "amount": "90000.00" },
    { "accrualId": "c9331c61-0208-4f05-a4ec-3b056464243a", "amount": "40000.00" }
  ]
}
```

В примере `20000.00` остается нераспределенным авансом.

## 10. Клиентская функциональность

### 10.1. Раздел «Финансы»

Добавить пункт верхнего уровня в боковом меню и маршрут `/finance`. Страница содержит:

- сводные карточки «Начислено», «Оплачено», «Долг», «Аванс», «Не распределено»;
- вкладку «Оплаты»;
- вкладку «Начисления»;
- вкладку «По заказчикам»;
- вкладку «Отчеты»;
- основные действия «Добавить оплату» и «Добавить начисление».

В таблице оплат показываются дата, заказчик, способ, сумма, распределено, остаток и статус. Раскрытие строки показывает заказы/услуги, на которые направлены деньги.

В таблице начислений показываются дата, заказчик, источник, сумма, оплачено, остаток и состояние. Для заказа название является ссылкой на существующую страницу `/order/:groupID`.

### 10.2. Форма оплаты

Обязательные поля:

- заказчик;
- дата;
- способ;
- сумма.

Необязательные поля: внешний номер и комментарий. После выбора заказчика ниже появляется таблица его активных начислений с остатками и полями распределения. В форме постоянно видны:

- сумма оплаты;
- распределено;
- останется авансом.

Нельзя выбрать начисление другого заказчика или ввести отрицательную сумму. Сохранение отправляет оплату и все начальные распределения одной командой.

### 10.3. Перераспределение

Карточка оплаты открывает тот же редактор распределения. Клиент отправляет полную желаемую карту активных распределений и `expectedVersion`, а сервер атомарно освобождает измененные строки и создает новые. При `409` клиент перечитывает оплату и предлагает повторить изменения на свежих данных.

### 10.4. Страница заказа

На существующей странице заказа добавить компактный финансовый блок:

- рассчитано по документам;
- начислено;
- оплачено по распределениям;
- остаток;
- нераспределенный аванс этого заказчика;
- действия «Создать/обновить начисление» и «Добавить оплату».

Нераспределенный аванс заказчика показывается отдельно и не подписывается как оплата этого заказа.

### 10.5. Карточка заказчика

Текущие заказчики отображаются как общий каталог без отдельной страницы. Для MVP достаточно перехода из финансовой таблицы на фильтр `/finance?customerId=...`. Выделенную страницу заказчика следует создавать только если она понадобится не только финансовому разделу.

## 11. Клиентская архитектура по FSD

Начать с page-local реализации и извлекать части только при подтвержденном повторном использовании:

```text
client/src/pages/finance/
  api/
  model/
  ui/
  index.ts
```

На странице `pages/finance` остаются таблицы, фильтры, формы, экспорт и координация запросов. Транспортные функции и базовые response-типы используют существующий API-клиент в `shared/api`/`shared/lib/swr` без создания нового универсального CRUD-хука.

Когда финансовая сводка будет одновременно использоваться на `/finance` и `pages/order`, общую read-модель и минимальные компоненты можно вынести в `entities/finance`. Форму оплаты следует выделять в `features/record-payment` только при реальном использовании минимум в двух местах. Страница связывает feature и сущности; прямые импорты feature из feature запрещены.

Данные сервера остаются в SWR. В Zustand не нужно копировать списки оплат и начислений; локально хранятся только черновик формы, фильтры и временное распределение. После мутаций инвалидируются ключи оплаты, начисления, заказчика, заказа и общей сводки.

Статические стили оформляются через Emotion. `style` допустим только для действительно вычисляемых значений, например ширины индикатора оплаты.

## 12. Отчеты

### 12.1. Отчет по оплатам

Строки: дата, заказчик, способ, сумма, распределено, не распределено, внешний номер, статус. Итоги группируются по способу оплаты и выводятся общей суммой.

### 12.2. Отчет по начислениям

Строки: дата, заказчик, источник, заказ/услуга, первоначальная сумма, корректировки, итоговая сумма, оплачено распределениями, остаток, статус.

### 12.3. Акт взаиморасчетов по заказчику

В хронологическом порядке выводятся начисления, корректировки и оплаты. Обязательные итоги:

- сальдо на начало периода;
- начислено за период;
- оплачено за период;
- сальдо на конец периода;
- отдельно нераспределенный аванс на конец периода.

События одной календарной даты сортируются по `createdAt`, затем `id`; это технический порядок, а не банковская очередность.

### 12.4. Экспорт

MVP экспортирует текущий отфильтрованный отчет в XLSX через уже установленный `@protobi/exceljs`. Сервер возвращает данные и агрегаты, клиент формирует файл. В выгрузке фиксируются выбранные фильтры и время формирования. PDF и печатные формы не входят в первую версию.

## 13. Согласованность с жизненным циклом заказа

Финансовый и производственный статусы независимы:

- перевод заказа в `in_production` не создает начисление автоматически;
- `completed` не означает «оплачен»;
- `cancelled` не означает автоматическое аннулирование начисления или возврат оплаты;
- полностью оплаченный заказ не переводится автоматически в `completed`;
- изменение производственной доски и custom status не влияет на финансы.

Такое разделение необходимо, потому что отмененный заказ может содержать фактически оказанные услуги и долг, а завершенный заказ может оставаться неоплаченным.

Если позднее потребуется политика автоматического проведения при конкретном переходе статуса, она добавляется как отдельная бизнес-команда после согласования, а не как скрытый listener.

## 14. Конкурентность, целостность и безопасность

- Все денежные команды выполняются транзакционно.
- Команды изменения принимают `expectedVersion`; устаревшая версия дает `409`.
- `requestId` защищает создание оплаты и операции начисления от сетевого повтора.
- Сервер никогда не доверяет клиентским итогам `allocated`, `balance` и `orderTotal`; они рассчитываются заново.
- Сервер проверяет принадлежность начислений выбранному заказчику.
- Списки ID не подставляются в SQL строковой конкатенацией; используются параметры QueryBuilder.
- Текстовые поля имеют разумные лимиты и проходят существующую DTO-валидацию.
- Финансовые сущности не удаляются физически обычными API-командами.
- Поскольку авторизации нет, в MVP нельзя утверждать, какой менеджер выполнил операцию. Поле `actorId` не добавляется с фиктивным значением.

## 15. Миграция и запуск

### Этап 1. Надежная связь заказчика

1. Добавить `order_groups.customerId` и две миграции — PostgreSQL и SQLite.
2. Заполнить поле по `customer.id` из JSON только при точном совпадении существующего UUID.
3. Обновить создание и изменение заказа: сервер принимает ID, проверяет заказчика и формирует снимок.
4. Добавить диагностический список старых заказов без связи.
5. Ограничить физическое удаление связанных заказчиков.

### Этап 2. Финансовое ядро

1. Добавить четыре финансовые таблицы, ограничения и индексы в обе схемы БД.
2. Реализовать денежные преобразования, DTO и сервисы начислений/оплат/распределений.
3. Покрыть транзакции, конкурентность, идемпотентность и отмену unit/integration-тестами.
4. Не создавать начисления по существующим заказам автоматически.

### Этап 3. Рабочий интерфейс

1. Добавить `/finance`, навигацию, сводку и списки.
2. Добавить формы оплаты, ручного начисления и распределения.
3. Добавить финансовый блок заказа.
4. Проверить мобильную/узкую ширину, пустые состояния, большие списки и ошибки конкуренции.

### Этап 4. Отчеты и внедрение

1. Добавить серверные агрегаты и отчетные фильтры.
2. Добавить XLSX-экспорт.
3. Проверить обновление существующей PostgreSQL и SQLite БД на копиях.
4. Перед обновлением desktop сделать резервную копию SQLite, для web — штатный backup PostgreSQL.
5. После приемки включить раздел в обычную навигацию.

## 16. Обязательные проверки реализации

| Область | Сценарии |
| --- | --- |
| Связь заказчика | Валидный backfill по UUID; отсутствующий/поврежденный snapshot; запрет проведения без `customerId`; запрет удаления связанного заказчика |
| Начисление заказа | Сумма нескольких документов; пустой заказ; повторное проведение; изменение цены вверх/вниз; запрет снижения ниже оплаты |
| Ручное начисление | Создание услуги; обязательные поля; положительная сумма; аннулирование с причиной |
| Оплата | Наличные, карта, перевод, другое; оплата без распределения; полный и частичный аванс; повтор одного `requestId` |
| Распределение | Одна оплата на несколько заказов; несколько оплат на заказ; чужой заказчик; превышение оплаты; превышение остатка начисления |
| Перераспределение | Освобождение части; перенос между заказами одного заказчика; история released; атомарный rollback при ошибке одной строки |
| Аннулирование | Оплата с распределениями; повторная отмена; начисление без/с распределением; обязательная причина |
| Конкурентность | Два распределения одной версии: один успех, один `409`; параллельное уменьшение начисления и распределение; повторы после таймаута |
| Точность | Копейки, большие суммы, сумма из многих частей, отсутствие `0.1 + 0.2` ошибок, граница безопасного диапазона |
| Даты | Границы периода включены; операции в разные часовые зоны; одинаковая календарная дата; начальное сальдо |
| Отчеты | Итоги равны строкам; отмененные операции отражаются корректно; фильтры; пустой период; XLSX соответствует экрану |
| Жизненный цикл заказа | Завершение/отмена не меняет финансы; финансовый статус не меняет производство; удаление заказа с начислением запрещено |
| БД | Одинаковые ограничения в PostgreSQL и SQLite; миграция старой БД; FK check SQLite; rollback транзакции; индексы используются на больших выборках |
| UI | Пустые состояния, загрузка, повтор запроса, `409`, доступность формы, форматирование ₽, переход в заказ |

## 17. Критерии приемки MVP

Функциональность готова к использованию, когда выполняются все условия:

1. Менеджер может зарегистрировать оплату заказчика без выбора заказа.
2. Менеджер может сразу или позднее распределить одну оплату на несколько начислений.
3. Один заказ может быть оплачен несколькими частями.
4. Нельзя распределить больше суммы оплаты или больше остатка начисления.
5. Нераспределенный остаток виден как аванс заказчика и не считается оплатой конкретного заказа.
6. Заказ и ручная услуга создают начисления одного общего формата.
7. Изменение цены проведенного заказа создает явную корректировку и не переписывает старую операцию.
8. На странице заказа видны рассчитано, начислено, оплачено и остаток.
9. По заказчику видны общий долг/аванс и история операций.
10. Отчеты за период дают сверяемые итоги и выгружаются в XLSX.
11. Ошибочные записи аннулируются с причиной и не исчезают из истории.
12. Повтор запроса и конкурентные действия не создают двойную оплату и не нарушают суммы.
13. Все сценарии работают в PostgreSQL и SQLite после миграции существующей базы.

## 18. Подтвержденные решения

Для реализации подтверждены следующие решения:

1. Единица учета заказа — `OrderGroup`, а не отдельный документ `Order`.
2. Начисление по заказу проводится явным действием, а не автоматически при создании или смене статуса.
3. Валюта MVP — только RUB.
4. Способы оплаты фиксированы: наличные, карта, банковский перевод, другое.
5. Переплата конкретного заказа запрещена; остаток хранится как общий аванс заказчика.
6. Отмена заказа не аннулирует начисление автоматически.
7. Финансовые суммы после проведения исправляются отменой/корректировкой, а не обычным редактированием.
8. Первый формат выгрузки — XLSX; PDF не входит в MVP.

Декомпозиция и порядок реализации зафиксированы в [отдельном документе задач](financial-accounting-tasks.md), начиная с миграции связи `OrderGroup → Customer` и финансового ядра.
