# Управление заказами: задачи для AI-агента

Основа: [архитектура фичи](order-management-architecture.md), включая согласованные решения MVP в разделе 13. OM-01 и OM-02 реализованы; проверка PostgreSQL остаётся открытой. Остальные задачи пока не выполнены. Это задания на реализацию, а не создание отдельных задач в приложении Codex.

## Как передавать задачу агенту

Передайте общий контекст ниже и соответствующий раздел OM-XX. Агент должен прочитать архитектуру, проверить результат зависимых задач в текущем коде и реализовать только указанную задачу. Не начинать зависимую работу на предположении, что предыдущая задача уже выполнена.

Готовая формулировка запуска:

> Выполни задачу OM-XX из docs/order-management-tasks.md. Прочитай общий контекст, указанную задачу и связанные разделы docs/order-management-architecture.md. Проверь наличие результатов зависимостей. Соблюдай AGENTS.md. Реализуй задачу, добавь проверки изменённого поведения, выполни релевантные тесты и сборку. Не реализуй следующие задачи и не расширяй MVP. В итоговом отчёте перечисли изменения, проверки, оставшиеся ограничения и фактические API-контракты для следующего агента.

Если обнаружено противоречие, сначала проверить код и архитектуру. Локальные технические решения принимать самостоятельно; изменение согласованного продуктового поведения явно выносить на обсуждение. Если зависимость не реализована, сообщить конкретно, чего не хватает, не подменять её фиктивной реализацией.

## Общий контекст для каждой задачи

- Репозиторий: [AGENTS.md](../AGENTS.md), [client/package.json](../client/package.json), [server/package.json](../server/package.json).
- `OrderGroup` — заказ с существующим общим статусом. `Order` — документ заказа. Карточка доски соответствует одному документу, внутри документа один текущий этап.
- Существующий `draft / in_production / completed / cancelled` сохранить: он влияет на расчёт цен. Пользовательский статус и этап производства — отдельные данные.
- Прогресс определяется этапом; сводка группы — невзвешенное среднее всех документов, без карточки — 0%, для пустого заказа — отсутствие процента.
- Срок — календарная дата без времени, зона по умолчанию `Europe/Moscow`. Рабочие и выходные дни в MVP не различаются.
- Уведомления общие для установки, персональных получателей нет. Принять предложенные интервалы: серверная проверка раз в 5 минут, клиентский polling раз в 2 минуты, плюс начальная загрузка/проверка и восстановление подключения.
- Закрытый Electron не отправляет сообщения. После открытия допустимо получить актуальные напоминания. Не добавлять фоновую службу.
- Заказ закрывается явно; допускается закрытие без полного производственного учёта с причиной.
- Сервер: NestJS 11, TypeORM, PostgreSQL и SQLite. Каждому изменению схемы нужны миграции для обеих БД. Не использовать `synchronize: true`.
- Клиент: React 19, FSD, Emotion, Ant Design, SWR, Zustand; dnd-kit уже установлен. Статические стили через Emotion. Не добавлять вторую DnD/toast-библиотеку и не мигрировать общий слой запросов.
- Не добавлять Redis, BullMQ, SSE, WebSocket, произвольные скрипты условий, параллельные производственные задания, персонализацию и количественный учёт изготовления.
- При работе с NestJS применять доступный skill `nestjs-best-practices`, при размещении клиентских модулей — `feature-sliced-design`. Не делать попутный рефакторинг соседних сценариев.
- Технические контракты в архитектуре ориентировочные. Фиксировать выбранные DTO и endpoint в разделе выполненной задачи этого документа, если они отличаются; обновлять архитектуру только в затронутой части. Следующий агент использует фактический контракт.

## Общие критерии готовности

Каждая задача включает свой код, миграции при необходимости и тесты поведения. Не переносить их на OM-12. Изменения должны собираться самостоятельно после выполненных зависимостей.

- Проверить существующие тесты затронутых сценариев, новые ошибки и пограничные случаи; не писать тесты, только повторяющие реализацию.
- Для серверного поведения запускать релевантные Jest-тесты с coverage, для клиентского — Vitest с coverage. Использовать scripts пакетов и фильтры тестов; в итоговом отчёте указывать точные команды и результат.
- Для изменений данных проверять миграции и транзакционные инварианты на обеих БД. Если одна БД недоступна, явно указать непроверенную часть; не объявлять проверку пройденной.
- После изменений соответствующего пакета выполнить `npm run build`; для клиента проверить FSD через `npm run fsd:check`. Не запускать исправляющий lint на всём репозитории ради локальной задачи.
- Для UI проверить loading/error/empty states, клавиатуру и фактический экран. Если среда позволяет, приложить скриншоты видимых изменений.
- Не коммитить секреты. Не выполнять destructive down-миграции на пользовательской БД.

## OM-01. Базовая модель управления заказами и журнал

**Цель:** подготовить хранение сроков, пользовательских статусов, версий и истории без изменения текущей ценовой логики.

**Контекст:** архитектура, разделы 2, 6, 7 и 12. Точки входа: [OrderGroup](../server/src/modules/order-groups/entities/order-group.entity.ts), [Order](../server/src/modules/orders/entities/order.entity.ts), [DatabaseJsonColumn](../server/src/modules/database/database-json-column.ts), [настройки БД](../server/src/modules/database/database-options.ts), [AppModule](../server/src/app.module.ts).

**Реализовать:**

- Создать `OrderManagementModule`, сущности custom status, настроек зоны и журнала. Добавить `dueDate`, `customStatusId`, `managementVersion` группе и документу.
- Подготовить индексы, FK и совместимые типы для обеих БД. При удалении ссылки из истории обнуляются, снимки остаются.
- Добавить узкий сервис записи события через переданный transaction manager. Не вызывать notification delivery и не добавлять scheduler.
- Инициализировать одну запись настроек с `Europe/Moscow`. Не создавать доски, статусы и историю для старых заказов автоматически.
- Добавить парные аддитивные миграции с учётом существующих данных и уникальными именами относительно текущей ветки.

**Приёмка:** существующие заказы сохраняют статусы и цены; nullable-поля не требуют backfill из выдуманных значений; миграции применяются на старой и пустой SQLite и PostgreSQL; запись события откатывается вместе с транзакцией.

**Передать дальше:** точные сущности, типы событий, интерфейс записи журнала и имена миграций. Публичный CRUD и lifecycle входят в OM-02.

### Результат OM-01 (7 сентября 2026)

Реализован `server/src/modules/order-management/`: `OrderManagementModule` подключён в `AppModule`, регистрирует три сущности и экспортирует `OrderManagementEventService`. Новых HTTP endpoint нет.

Фактический контракт:

- `CustomOrderStatus` → `custom_order_statuses`: UUID `id`, `scope: 'group' | 'document'` (CHECK), `name`, `color`, целочисленный `position = 0`, nullable `archivedAt`.
- `OrderManagementSettings` → `order_management_settings`: числовой PK `id = 1` (CHECK ограничивает единственную запись), `timeZone`. Миграция создаёт запись `Europe/Moscow`.
- `OrderGroup` и `Order`: `dueDate: string | null` (SQL date, `YYYY-MM-DD`), `customStatusId: string | null` (UUID FK с RESTRICT), `customStatus: CustomOrderStatus | null`, `managementVersion: number = 0` (обычная integer-колонка). В OM-02 нужен условный UPDATE с проверкой ожидаемой версии; автоматического увеличения сейчас нет.
- `OrderManagementEvent` → `order_management_events`: UUID `id`, nullable `orderGroupId: number` и `orderId: string` с FK `SET NULL`; `type`, обязательные JSON `before`, `after`, `targetSnapshot`; nullable `reason`; `occurredAt` генерируется БД, `notificationProcessedAt` изначально null. В PostgreSQL времена — `timestamptz`, JSON — `jsonb`; SQLite — `datetime` и `simple-json` через `DatabaseJsonColumn`.
- `OrderManagementEventType`: `due_date_changed`, `custom_status_changed`, `lifecycle_changed`, `stage_changed`, `board_assigned`, `board_removed`, `board_changed`, `group_deleted`, `document_deleted`. Это TypeScript union, а не DB enum.
- `record(manager: EntityManager, event: WriteOrderManagementEvent): Promise<OrderManagementEvent>` требует активной транзакции переданного manager, иначе бросает Error. Сервис не открывает отдельную транзакцию и не отправляет уведомления.
- Вход журнала: необязательные `orderGroupId`, `orderId`, `reason`; обязательные `type`, `before`, `after`, `targetSnapshot`. `before/after` — `Record<string, ManagementEventValue>` с рекурсивными JSON-значениями. `targetSnapshot` содержит обязательные nullable `orderNumber: string`, `documentNumber: number`, `documentName: string`. Идентификаторы и названия статусов/этапов вызывающий сервис сохраняет в `before/after`. Снимки не содержат FK и переживают удаление исходного объекта.

Миграции: `1788800000000-AddOrderManagement.ts` / `AddOrderManagement1788800000000` в обеих папках `migrations/sqlite` и `migrations/postgres`. Имена уникальны внутри каждой цепочки. SQLite использует `migrationsTransactionMode: 'each'`: эта миграция отключает FK до начала собственной транзакции перестроения таблиц, выполняет `foreign_key_check` перед commit и восстанавливает FK в finally. Остальные SQLite-миграции выполняются в отдельных транзакциях. Для PostgreSQL режим не менялся. Команды `npm run migration:run:sqlite` и `npm run migration:revert:sqlite` используют этот режим из data source; не переопределять его на `all`.

Индексы: группа `(status, dueDate)`, документ `(dueDate)`, оба FK custom status, статусы `(scope, position)`, история `(notificationProcessedAt, occurredAt, id)`, `(orderGroupId, occurredAt, id)` и `(orderId, occurredAt, id)`. Существующий уникальный индекс документа `(orderGroupId, documentNumber)` покрывает поиск по группе.

Проверки из `server/`:

- `npm run test:cov -- --runInBand add-order-management.migration.spec.ts orders.service.spec.ts order-groups.service.spec.ts database-options.spec.ts --collectCoverageFrom=modules/order-management/**/*.ts --collectCoverageFrom=modules/database/migrations/sqlite/1788800000000-AddOrderManagement.ts` — 19 тестов; 100% строк сервиса журнала, 90,47% строк SQLite-миграции.
- `npm run test:e2e:sqlite` — 4 теста: полная цепочка миграций на пустой SQLite, отсутствие расхождений схемы с ORM, JSON, enum и FK.
- Новый migration spec проверяет обновление SQLite с существующими заказом, документом и позицией; сохранность цен и связей, отсутствие выдуманных данных, ограничения, откат журнала, сохранение снимков, повторное применение и down/up на одноразовой БД.
- `npm run build` — успешно. ESLint запускался без `--fix` только для затронутых серверных файлов.

Ограничения: реальный PostgreSQL недоступен (Docker отсутствует, `127.0.0.1:5432` не принимает соединение), поэтому его миграция и транзакции не проверены исполнением. Кроме того, существующая PostgreSQL-цепочка начинается с ALTER `price_modifiers`, без baseline: полная установка на физически пустую PostgreSQL уже требует исходной схемы и не решается аддитивной OM-01. Это необходимо закрыть перед окончательной приёмкой обеих БД. Проверки соответствия scope назначаемому объекту, архивности статуса, даты/зоны и интеграция журнала в команды относятся к OM-02; сейчас старые команды автоматически не пишут историю.

## OM-02. API пользовательских статусов, сроков и общего статуса

**Цель:** дать клиенту согласованный способ менять управленческие поля и исключить обход правил через старые endpoints.

**Контекст:** архитектура, разделы 4–7 и 9. Код: [OrderGroupsService](../server/src/modules/order-groups/order-groups.service.ts), [контроллер групп](../server/src/modules/order-groups/order-groups.controller.ts), [UpdateOrderGroupDto](../server/src/modules/order-groups/dto/update-order-group.dto.ts), [OrdersService](../server/src/modules/orders/orders.service.ts), [контроллер документов](../server/src/modules/orders/orders.controller.ts).

**Реализовать:**

- CRUD/архивирование custom status с `scope: group/document`, валидацией названия, цвета и ссылок. Архивный статус отображается у старого объекта, но недоступен для нового назначения.
- `PATCH .../management` для группы и документа, GET/PATCH настроек зоны и историю с пагинацией. Срок документа наследует срок группы только при отсутствии собственного.
- Условное изменение `managementVersion`, `409` при конфликте и атомарную запись before/after. Обычный `save` без проверки версии недостаточен.
- Общую проверку lifecycle, используемую также старым PATCH. Сохранить действующие расчёты при запуске; запретить неявный возврат в draft. Возобновление terminal-заказа и закрытие без полного учёта требуют причины.
- Пока карточек нет, закрытие проходит через явное подтверждение отсутствия полного учёта. После OM-04 проверка должна использовать реальную производственную готовность, без заглушки «все готовы».
- Закрыть пути обхода через обычный update, copy и delete: управленческие поля не копируются бесконтрольно, история удаления сохраняет снимки.

**Приёмка:** неправильный scope/дата/зона отклоняется; статус не меняет ценовую семантику; два изменения одной версии не затирают друг друга; старый endpoint не обходит lifecycle; изменение срока группы корректно влияет на наследуемый срок документа.

**Передать дальше:** примеры запросов/ответов management, lifecycle, history и settings, включая версии и подтверждение закрытия. Не реализовывать UI.

### Результат OM-02 (7 сентября 2026)

`OrderManagementService` и три контроллера зарегистрированы в `OrderManagementModule`. Модуль экспортирует сервис, импортируется модулями заказов и документов без обратных импортов. Новых колонок и миграций нет. Фактические endpoints имеют префикс `/api`:

| Endpoint | Контракт |
| --- | --- |
| `GET /order-management/statuses?scope=group` | Все статусы выбранного scope, включая архивные, `{ items, meta: { count } }`; scope необязателен, порядок position/id |
| `POST /order-management/statuses` | `{ scope: "group" или "document", name, color, position? }`; ответ — сущность, HTTP 201 |
| `PATCH /order-management/statuses/:id` | `{ name?, color?, position? }`; scope неизменяемый, ответ — сущность |
| `POST /order-management/statuses/:id/archive` | Идемпотентная архивация, ответ — сущность, HTTP 201 |
| `DELETE /order-management/statuses/:id` | Только неиспользованный статус; назначение или запись custom_status_changed в истории → 409; ответ `{ id }` |
| `GET/PATCH /order-groups/:id/management` | Представление/изменение полей группы, включая lifecycle |
| `GET/PATCH /orders/:id/management` | Представление/изменение полей документа, без собственного lifecycle |
| `GET/PATCH /order-management/settings` | `{ id: 1, timeZone }`; PATCH принимает `{ timeZone: "Europe/Moscow" }` |
| `GET /order-management/history?orderGroupId=1&orderId=<uuid>&offset=0&limit=50` | Фильтры необязательны, вместе означают AND; `{ items: OrderManagementEvent[], meta: { nextOffset: number или null } }` |

Имя статуса обрезается по краям, длина 1–100; цвет — `#RRGGBB`; position — целое 0–1 000 000. Архивный статус остаётся в представлении назначенного объекта. Его повторное указание без изменения назначения разрешено; новое назначение запрещено. При очистке назначения или собственного срока передавать `null`; отсутствие поля означает «не менять». Даты валидируются как реальные `YYYY-MM-DD`, включая високосные годы, без времени и преобразования через UTC. Зона — поддерживаемое IANA-имя или `UTC`. Boolean и expectedVersion в JSON не приводятся из строк.

Пример изменения группы:

```http
PATCH /api/order-groups/1/management
Content-Type: application/json

{ "expectedVersion": 0, "dueDate": "2026-09-10", "customStatusId": null }
```

```json
{
  "id": 1,
  "dueDate": "2026-09-10",
  "effectiveDueDate": "2026-09-10",
  "customStatusId": null,
  "customStatus": null,
  "managementVersion": 1,
  "status": "draft"
}
```

Пример изменения документа:

```http
PATCH /api/orders/<uuid>/management
Content-Type: application/json

{ "expectedVersion": 0, "dueDate": null }
```

Ответ: `{ id: <uuid>, orderGroupId: 1, dueDate: null, effectiveDueDate: "2026-09-10", customStatusId: null, customStatus: null, managementVersion: 1 }`. Собственный срок имеет приоритет; наследуемый вычисляется при чтении, не записывается в документ. Изменение срока группы не создаёт искусственные события для каждого наследующего документа.

`expectedVersion` обязателен для обоих management PATCH, целое >= 0. Используется условный UPDATE версии, затем чтение заблокированного объекта и запись событий в той же транзакции. Несовпадение — 409; отсутствие объекта — 404. Каждый успешный management PATCH, включая отсутствие фактических изменений, увеличивает версию; события создаются только для изменившихся полей. Изменение документа также атомарно увеличивает managementVersion его группы: клиенту нужно обновить представление группы. Порядок блокировок — группа, документ, назначаемый статус. Назначение статуса сериализуется с архивированием/удалением.

Lifecycle передаётся полем `status` в management PATCH группы. Старый `PATCH /order-groups/:id` при наличии status требует тот же expectedVersion, допускает reason/confirmIncompleteProduction и вызывает ту же проверку; обычные поля в смешанном запросе сохраняются атомарно с переходом.

```json
{ "expectedVersion": 1, "status": "in_production" }
```

```json
{ "expectedVersion": 2, "status": "completed", "confirmIncompleteProduction": true, "reason": "Производство закрыто без полного учёта" }
```

```json
{ "expectedVersion": 3, "status": "in_production", "reason": "Возобновление для переделки" }
```

Переход назад в draft запрещён. Из completed/cancelled допустим только переход в in_production с непустой причиной. Причина после trim — 1–1000 символов. Пока карточек нет, каждое фактическое закрытие требует `confirmIncompleteProduction: true` и reason. OM-04 должна заменить это условие фактической проверкой готовности; текущая реализация не считает документы готовыми. Смена статуса сама по себе не пересчитывает цены и не переписывает startedAt, как и прежний серверный PATCH. Существующие явные команды пересчёта сохранены.

Старые endpoints не принимают dueDate/customStatusId/managementVersion. Не сохранявшийся ранее `status` исключён из DTO документа: теперь такой PATCH даёт 400. Обычное сохранение документа и пересчёт производства группы записывают только редактируемые поля, не переносят загруженные ранее management-поля в UPDATE. Копия документа получает null срок/статус, версию 0, без истории; наследование срока группы действует и для копии.

Удаление документа/группы записывает событие в той же транзакции. FK истории обнуляются, JSON-снимки остаются. Удаление группы сохраняет прежнюю семантику: документы не удаляются, а становятся без группы; их версии увеличиваются, поскольку меняется наследуемый срок. История удалённых объектов доступна в общей ленте без фильтра по живому FK. Пагинация истории использует offset/limit (limit 1–100), порядок occurredAt DESC/id DESC; при появлении новых событий клиенту следует обновить первую страницу.

Для SQLite команды управления последовательно используют единственное соединение better-sqlite3; для SQLITE_BUSY/SQLITE_BUSY_SNAPSHOT предусмотрены максимум две повторные попытки всей транзакции. PostgreSQL использует транзакции и условные UPDATE без локальной очереди. Внешних вызовов внутри транзакций нет.

## OM-12. Сквозная приёмка MVP на PostgreSQL и Electron/SQLite

**Цель:** проверить совместную работу всех частей, миграцию существующей установки и поведение после выхода из приложения.

**Контекст:** архитектура, разделы 12–13; [SQLite e2e](../server/test/database-sqlite.e2e-spec.ts), [конфигурация e2e](../server/test/jest-e2e.json), [MSW](../client/src/shared/api/mocks/handlers.ts), [desktop README](../desktop/README.md), [корневой package.json](../package.json).

**Выполнить:**

- Проверить цепочку: создать custom status и доску → назначить два документа одного заказа → запустить заказ → развести документы по этапам → проверить процент и срок → создать правило → получить сообщение → перейти к документу → закрыть заказ явно.
- Проверить отмену/возобновление, закрытие без полного учёта с причиной, копирование документа без карточки, архивирование используемых сущностей, удаление заказа с историей и уведомлениями.

- На копиях БД проверить обновление старой установки и свежую установку обеих БД. Старые заказы не получают вымышленные этапы, сроки или историю.
- Проверить упакованный Electron: дата и HashRouter-ссылка корректны; выход останавливает проверки; после открытия появляется актуальное напоминание без серии пропущенных ежедневных сообщений.

- На согласованном тестовом окружении измерить набор из архитектуры: 10 000 документов, 100 правил, до 200 загруженных карточек. Проверить длительность прохода и запросов; зафиксировать реальные значения и окружение.
- Дополнить документацию фактическими командами миграции/запуска, новой конфигурацией и ограничениями. Не включать пользовательские правила автоматически и не разворачивать релиз без отдельного запроса.

**Приёмка:** приложен отчёт с пройденными сценариями, командами, измерениями и явно непроверенными частями; существенные дефекты устранены; подтверждены шесть согласованных решений MVP. Не требуется добавлять новую платформу e2e-тестов, если существующих тестов и документированной ручной проверки достаточно.
