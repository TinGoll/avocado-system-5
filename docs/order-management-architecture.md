# Управление заказами: доски, статусы и уведомления

Дата: 7 сентября 2026. Статус: продуктовые границы MVP согласованы; архитектурное предложение для последующей реализации.

Документ описывает изменения применительно к текущему репозиторию. Код приложения и зависимости в рамках этой задачи не изменяются. Согласованные решения MVP зафиксированы в разделе 13; технические детали остаются предложением по реализации, а не уже существующим поведением.

План реализации: [задачи для AI-агента с зависимостями и критериями готовности](order-management-tasks.md).

## 1. Предлагаемое решение

Добавить настраиваемые производственные доски: пользователь создаёт колонки, задаёт их порядок перетаскиванием и перемещает между ними документы заказов. На карточке видны заказ, документ, срок, пользовательский статус и оценка прогресса. На странице заказа показывается сводка по всем документам.

Разделить три понятия:

1. **Общий статус заказа** — существующий жизненный цикл `draft / in_production / completed / cancelled`.
2. **Пользовательский статус** — настраиваемая отметка заказа или документа: «Ожидает материала», «Согласование», «Переделка».
3. **Производственный этап** — положение документа на доске: «Очередь», «Раскрой», «Покраска», «Сборка», «Готово».

Напоминания рассчитывает сервер по сохранённым правилам. Результаты сохраняются в БД, клиент получает их периодическими HTTP-запросами и показывает через Ant Design справа внизу. История уведомлений доступна отдельно: закрытие всплывающего сообщения не должно приводить к потере информации.

Начальный вариант использует существующие PostgreSQL/SQLite, dnd-kit, SWR и Ant Design. Единственная обязательная новая runtime-зависимость — `@nestjs/schedule`. Redis, отдельный worker и WebSocket для первого релиза не нужны.

## 3. Границы первой версии

### Включить

- Несколько досок, создание и настройку колонок, drag-and-drop колонок и карточек.
- Одну производственную карточку на документ и не более одной доски для документа одновременно.
- Пользовательские статусы отдельно для группы и документа; один выбранный статус на объект.
- Срок заказа, необязательный отдельный срок документа, сводку производства на странице заказа.
- Историю изменений этапа, пользовательского статуса, срока и общего статуса.
- Настраиваемые напоминания о сроках и событиях изменения, предпросмотр текста.
- Общую ленту уведомлений этой установки, прочтение и всплывающие сообщения со ссылками.
- Работу с обеими БД, восстановление актуальных напоминаний после перезапуска.

### Отложить

- Параллельное производство частей одного документа, партии и учёт количества готовых изделий.
- Граф маршрутов с зависимостями, обязательными переходами и ветвлениями.
- Автоматическое планирование загрузки станков, нормы времени и точный процент трудозатрат.
- Учёт рабочих и выходных дней при расчёте сроков и напоминаний; возможное расширение после MVP.
- Email, Telegram, системные push-уведомления, персональных получателей и роли.
- Произвольный JavaScript/SQL в условиях, визуальный язык программирования правил.

Документы одного заказа уже могут выполняться параллельно. Если нужна параллельная покраска и сборка внутри одного документа, потребуется отдельная модель производственных заданий. Дублировать карточку документа ради этого нельзя: появятся противоречивые состояния.

## 4. Поведение доски и статусов

### Единица управления

Карточка представляет `Order`, а не `OrderGroup`. Например, заказ № 123 содержит документы № 1 «Фасады» на покраске и № 2 «Корпуса» на сборке. Страница заказа показывает оба этапа и общий прогресс. Группу целиком не перетаскиваем: пакетное перемещение документов можно добавить отдельно.

Документы без группы допускаются текущей моделью, но в MVP не назначаются на производство до включения в заказ. Новый или скопированный документ не наследует карточку, историю и завершённость исходного документа.

### Настройка

Доска содержит имя, описание и упорядоченные колонки. Колонка содержит имя, цвет, тип `queue / active / done` и оценку прогресса при нахождении в ней. Требуются хотя бы одна `queue`, одна `active` и одна `done`; начальная колонка выбирается явно среди `queue`.

Пользователь может переименовать «Покраску» в «Покрасочный цех» без изменения идентификатора. Названия не используются как ключи правил. Порядок колонок — порядок отображения, а не автоматически вычисляемая степень готовности.

В MVP переименование, цвет, добавление и визуальная перестановка колонок разрешены на работающей доске. Тип и процент колонки после первого использования фиксируются. Для изменения их смысла создаётся новая колонка с явным перемещением карточек. Это позволяет обойтись без версионирования всего маршрута и не менять прогресс существующих документов незаметно.

Пустую неиспользованную колонку можно удалить. Использованную — архивировать после переноса активных карточек; если на неё ссылается включённое правило, сначала обновить или выключить правило. Архивная колонка недоступна для новых перемещений, но остаётся в истории. Доску с незавершёнными карточками архивировать нельзя. Переход на другую доску выполняется отдельной явной командой с выбором колонки, записью истории и пересмотром прогресса.

### Общий жизненный цикл

Существующее `OrderGroup.status` остаётся источником решения для текущей ценовой логики. Пользовательская отметка его не меняет. Этап `done` означает производственную готовность документа, а `completed` — закрытие заказа; эти действия не тождественны.

Предлагаемые ограничения новых команд:

| Действие | Результат |
| --- | --- |
| Назначить документ на доску | Разрешено для `draft` и `in_production`; у черновика только очередь |
| Начать работу над документом черновика | UI предлагает явную команду запуска заказа; после неё разрешён активный этап |
| Перевести группу в `in_production` | Сохраняется существующая семантика запуска и расчётов; документы не обязаны переместиться одновременно |
| Достичь `done` всеми документами | Показать «Производство завершено» и действие закрытия заказа; не менять `completed` автоматически |
| Закрыть заказ | Все документы должны иметь карточку в `done`, либо пользователь явно подтверждает закрытие без полного учёта производства с причиной |
| Отменить заказ | Этапы сохраняются для истории, карточки уходят из активного вида, напоминания о сроках прекращаются |
| Возобновить завершённый/отменённый заказ | Явное действие с причиной возвращает `in_production`; положение карточек сохраняется |

Прямой переход активного заказа назад в `draft` в новых командах запрещён: он затрагивает правила пересчёта. Нужность такого сценария согласовать отдельно. Существующие endpoints изменения общего статуса должны вызывать ту же проверку, иначе ограничения можно будет обойти обычным PATCH.

«Ожидает материала», «Приостановлен», «Переделка», «Готов к отгрузке» предлагаются как примеры пользовательских статусов, не как дополнительные enum-значения. Пользовательский статус — самостоятельная отметка: «Приостановлен» по умолчанию не останавливает календарный срок. Для исключения таких документов пользователь явно задаёт фильтр правила.

Оплата и доставка — отдельные будущие измерения. Не выводить их автоматически из стадии производства и не включать сейчас без соответствующих данных.

## 5. Прогресс и сроки

### Прогресс

В первой версии прогресс — **оценка по текущему этапу**, а не процент физически изготовленной продукции. Пример: очередь — 0%, раскрой — 10%, покраска — 45%, сборка — 75%, готово — 100%. Для `active` допустимы 1–99%, для `queue` только 0%, для `done` только 100%.

При перемещении карточки сервер записывает процент целевой колонки в карточку. Обратное перемещение уменьшает прогресс; переход через несколько колонок разрешён и не означает, что пропущенные операции подтверждены. Ручной независимый процент в MVP не вводится, чтобы не иметь двух конфликтующих источников.

Сводка группы: среднее арифметическое процентов всех текущих документов. Документ без карточки учитывается как 0%; рядом обязательно показывается «На доске: 2 из 3 документов». У пустого заказа процент отсутствует. Добавление нового документа может уменьшить общий процент. Отмена группы не превращает его в 100%.

Например: документы 45%, 75% и без карточки дают 40%. Это невзвешенная оценка: документ на одну позицию имеет тот же вес, что и документ на сто позиций. UI обозначает это как «Прогресс по этапам». Взвешивание по трудозатратам можно добавить только после появления достоверных нормативов; цена и `productionOperationResults` не являются фактом выполненной работы.

### Сроки

Добавить `dueDate` группе и документу — календарную дату `YYYY-MM-DD`, nullable. Эффективный срок документа: собственный `dueDate`, иначе срок группы. Изменение срока группы влияет на документы без собственного срока.

В настройках управления заказами хранить IANA time zone, по умолчанию `Europe/Moscow`, с возможностью изменения. Для MVP согласована календарная дата без времени суток: заказ со сроком 10 сентября просрочен с 00:00 11 сентября в выбранной зоне. «За 2 дня» означает начало 8 сентября; рабочие, выходные дни и праздники пока не различаются. Учёт рабочих и выходных дней можно добавить после MVP.

Даты без времени не преобразовывать через UTC-полночь на клиенте. Времена событий и запуска проверок хранить в UTC; сравнение календарных дат выполнять в настроенной зоне. Использовать один `now` на проход проверки. Смена зоны требует предпросмотра затронутых напоминаний и пересчёта текущих условий.

## 6. Модель данных

Ниже логическая схема. Имена таблиц и колонок уточняются при реализации по соглашениям TypeORM. Все новые идентификаторы могут быть UUID; существующий числовой `OrderGroup.id` сохраняется.

| Сущность | Основные поля и ограничения |
| --- | --- |
| `OrderGroup` — дополнение | `dueDate?`, `customStatusId?`, `managementVersion` для конкурентных изменений управленческих полей |
| `Order` — дополнение | `dueDate?`, `customStatusId?`, `managementVersion`; отдельный общий lifecycle документа не добавляется |
| `CustomOrderStatus` | `id`, `scope: group/document`, `name`, `color`, `position`, `archivedAt?`; FK проверяется вместе со scope |
| `ProductionBoard` | `id`, `name`, `description?`, `initialStageId`, `version`, `archivedAt?` |
| `ProductionStage` | `id`, `boardId`, `name`, `color`, `kind`, `progressPercent`, `position`, `usedAt?`, `archivedAt?` |
| `ProductionCard` | `id`, уникальный `orderId`, `stageId`, `position`, `progressPercent`, `enteredStageAt`, `version` |
| `OrderManagementEvent` | `id`, ссылка на группу и/или документ, `type`, `before/after`, `occurredAt`, `notificationProcessedAt?`; снимок номера заказа и названий для истории |
| `NotificationRule` | `id`, `name`, `enabled`, `revision`, `scope`, `trigger`, типизированные `conditions`, `repeat`, `messageTemplate`, `severity`, `activatedAt` |
| `Notification` | `id`, уникальный `dedupKey`, `ruleId?`, `ruleRevision`, ссылки на объект, снимок текста и link-токенов, `createdAt`, `readAt?`, `resolvedAt?` |
| `OrderManagementSettings` | Одна запись: `timeZone`; хранить вместе с валидацией поддерживаемой зоны |

Отдельный `boardId` в карточке не обязателен: доска однозначно определяется через `stageId`. При назначении сервер проверяет, что целевая колонка принадлежит указанной доске. История всегда содержит идентификаторы и снимки старых названий, поэтому переименование не переписывает прошлое.

JSON-колонки использовать через существующий `DatabaseJsonColumn`. Поисковые поля, дедлайны, версии, FK и ключ дедупликации хранить отдельными колонками; не прятать всю модель в `characteristics`.

Индексы: `ProductionStage(boardId, position)`, `ProductionCard(stageId, position, id)`, уникальный `ProductionCard(orderId)`, `OrderGroup(status, dueDate)`, `Order(dueDate)`, `Order(orderGroupId)`, `OrderManagementEvent(notificationProcessedAt, occurredAt, id)`, `Notification(readAt, createdAt, id)`, уникальный `Notification(dedupKey)`. Не полагаться на уникальность `position`; сервер нормализует целочисленные позиции в транзакции. Дополнительно проверить планы запросов для наследуемых сроков.

Статусы и правила, которые уже использовались, архивировать или выключать, сохраняя ссылки. В MVP не удалять историю и ключи отправленных уведомлений по таймеру. При удалении заказа в одной транзакции удалить его карточки, пометить актуальные уведомления завершёнными и обнулить ссылки исторических записей, сохранив снимки. Ссылка в таком сообщении становится недоступной.

## 7. Серверная архитектура и согласованность

### Модули

- `OrderManagementModule` (`modules/order-management`) владеет справочником статусов, изменением сроков, правилами общего статуса и журналом изменений. Экспортирует узкие сервисы для этих операций и записи истории через переданный transaction manager.
- `ProductionBoardsModule` (`modules/production-boards`) владеет досками, колонками и карточками. Использует журнал из `OrderManagementModule`.
- `NotificationsModule` (`modules/notifications`) владеет правилами, проверками, сохранёнными уведомлениями и чтением ленты. Читает события и необходимые проекции через TypeORM; модуль заказов не вызывает доставку уведомлений.
- `ScheduleModule.forRoot()` подключается один раз в `AppModule`.

Существующие `OrdersModule`/`OrderGroupsModule` используют `OrderManagementModule` для управленческих изменений и истории. Сам `OrderManagementModule` не импортирует их обратно: получает необходимые репозитории через `TypeOrmModule.forFeature`. Общая проверка переходов находится в одном сервисе. Не дублировать текущие ценовые расчёты в новом модуле и не использовать `forwardRef` для сокрытия циклов.

Объём необходимой интеграции: все пути изменения lifecycle, сроков, custom status и удаления объектов должны поддерживать новые инварианты и историю. Остальные CRUD и расчётные сервисы не рефакторить.

### Перемещение карточки

1. Клиент отправляет целевой этап, соседнюю карточку для вставки, ожидаемые версии карточки, доски и группы.
2. В транзакции сервер сначала выполняет условное обновление `managementVersion` группы, затем атомарно увеличивает `board.version` по ожидаемой версии. При несовпадении любой версии — откат и `409 Conflict`.
3. Проверяет актуальные lifecycle группы, принадлежность колонок, архивность и ожидаемую версию карточки. Все команды изменения общего статуса используют ту же сериализацию группы.
4. Меняет этап, целочисленные позиции затронутых колонок, процент, `enteredStageAt` и версию карточки. При перестановке внутри той же колонки не сбрасывает `enteredStageAt` и не создаёт событие смены этапа.
5. Записывает событие перехода и фиксирует транзакцию. Любая ошибка откатывает весь набор изменений.

Порядок блокировок во всех связанных командах единый: группа, затем доски в порядке ID, затем карточки. Перенос между досками захватывает обе версии. Настройка колонок и назначение/снятие карточек тоже изменяют версию доски. Так проверка целевого этапа не расходится с конкурентной архивацией.

Нельзя рассчитывать только на автоматический `@VersionColumn` при обычном `save`: необходим явный условный UPDATE и проверка числа изменённых строк. Для SQLite держать транзакции короткими и обрабатывать `SQLITE_BUSY` ограниченным повтором всей операции; для PostgreSQL использовать те же проверки версий. Сетевые вызовы в транзакции не выполнять.

UI оптимистично показывает перенос и блокирует повторный перенос этой карточки до ответа. При отказе откатывает изменение и обновляет данные SWR. При `409` сообщает, что доску изменили в другом окне, и предлагает повторить действие после обновления. После сетевого тайм-аута сначала перечитывает карточку: операция могла сохраниться. Устаревшая версия не должна создать второе событие при повторе запроса.

## 8. Правила уведомлений

### Что настраивает пользователь

Форма правила: название, включено/выключено, объект «заказ/документ», событие, условия, периодичность, важность и текст. Пользователь выбирает из поддерживаемых событий, а не создаёт исполняемый код.

| Триггер | Параметры | Семантика |
| --- | --- | --- |
| `due_soon` | За N календарных дней | От даты `dueDate - N` до конца срока включительно |
| `overdue` | С даты просрочки | Эффективный срок раньше сегодняшней даты |
| `stage_stalled` | Более N календарных дней на этапе | От локальной даты входа в этап + N; только документ |
| `stage_changed` | Исходный/целевой этап, необязательно | Каждое сохранённое событие перехода |
| `custom_status_changed` | Исходный/целевой статус, необязательно | Каждое сохранённое событие изменения отметки |
| `lifecycle_changed` | Исходный/целевой системный статус | Событие изменения группы, включая завершение и отмену |

Условия первой версии объединяются через AND: набор системных статусов, пользовательских статусов, досок и этапов. Внутри одного набора — OR. Исключения оформляются явно, например `customStatusNotIn`. Ограничить число значений и длину текста. Неподдерживаемые поля и несовместимые со scope условия отклонять через DTO-валидацию; ID проверять на существование.

У группы может быть несколько этапов одновременно. Для правила scope `group` фильтр по доске/этапу означает «есть хотя бы один документ на подходящем этапе»; одно уведомление на группу. Для scope `document` проверяется сама карточка. Правила срока группы и документов включаются независимо: интерфейс предпросмотра должен показывать возможные совпадения, по умолчанию включать напоминание только по группе.

Временные правила по умолчанию исключают `completed/cancelled`. Для документа дополнительно исключается `done`; без карточки документ участвует в напоминаниях о сроке, но не о простое на этапе. Событийные правила могут сообщать о завершении/отмене и не используют это исключение.

Повторы временных правил: один раз на актуальный срок/вход в этап либо один раз за календарный день. Событийные — один раз на событие. Временные правила создают только актуальный экземпляр: после недели простоя приложения не нужно показывать семь одинаковых ежедневных сообщений.

### Текст и ссылки

Пример шаблона:

```text
Заказ {{order.number}}: срок {{dueDate}}.
Документ {{document.number}} находится на этапе {{stage.name}}.
{{order.link}} {{document.link}}
```

Переменные доступны по scope; `document.*` в правиле группы недопустимы. В редакторе есть список переменных и предпросмотр на выбранном заказе. Нужные значения вычисляются в типизированном контексте, без доступа к произвольным свойствам объектов.

Текст разбирается небольшим собственным парсером ограниченных токенов: обычный текст + разрешённые переменные + специальные link-токены. HTML, JS, выражения и произвольные URL не поддерживаются. Сервер сохраняет снимок текста и структурированный target ссылки; клиент выводит текст React-узлами и link-токены через React Router. Не использовать `dangerouslySetInnerHTML`.

Target документа содержит ID группы и документа. Клиент разрешает актуальный `documentNumber` и формирует существующий путь `/order/<groupId>?document=<number>`; target заказа — `/order/<groupId>`. Не сохранять hostname или локальный порт Electron. Router сам учитывает BrowserRouter/HashRouter. Если документ удалён или больше не принадлежит группе, открыть доступную страницу группы с пояснением либо показать «Объект удалён».

### Планировщик и отсутствие повторов

Для MVP предлагается один проход раз в 5 минут через `@nestjs/schedule`, плюс проход после готовности БД при запуске. Пользователь допускает задержки больше минуты; 5 минут — предлагаемое техническое значение, а не требование к точности доставки. `waitForCompletion: true` предотвращает перекрытие cron-вызовов в одном процессе; общий локальный флаг/guard также охватывает стартовый вызов. Это не межпроцессная блокировка. [Документация NestJS Scheduling](https://docs.nestjs.com/techniques/task-scheduling).

Алгоритм:

1. Зафиксировать время прохода, загрузить включённые правила и их revisions.
2. Для временных правил выбирать кандидатов по сроку/этапу порциями, без eager-загрузки позиций заказа. Для событийных — читать необработанные записи журнала.
3. В короткой транзакции повторно проверить актуальную версию правила и состояние объекта. Для временной проверки использовать тот же механизм сериализации группы/карточки, что и команды изменения.
4. Сформировать стабильный `dedupKey` и вставить уведомление с обработкой конфликта уникальности как «уже создано». Не делать отдельные `exists` + `insert` без уникального индекса.
5. Для события вставка всех уведомлений и отметка `notificationProcessedAt` выполняются одной транзакцией. При ошибке событие остаётся необработанным. Журнал здесь одновременно служит простой долговечной очередью событий; дополнительный outbox для MVP не требуется.

Ключи дедупликации:

- событие: `ruleId + ruleRevision + eventId`;
- срок, однократно: `ruleId + ruleRevision + targetId + effectiveDueDate`;
- простой: `ruleId + ruleRevision + cardId + enteredStageAt`;
- ежедневный повтор: к соответствующему ключу добавить локальную календарную дату текущей проверки.

Одна и та же дата срока после временного переноса назад повторно не уведомляет однократным правилом. Если нужно повторное уведомление — использовать ежедневный режим или явно обновить правило. Это осознанная семантика MVP, исключающая отдельную таблицу эпизодов для каждого условия.

Любое сохранение изменённого правила увеличивает revision; новые временные проверки могут создать новый экземпляр для уже подходящих заказов. Предпросмотр предупреждает об этом. Новая revision действует на события с момента её активации; старые события ею не переигрываются. Если правило успели изменить до обработки события, применяется только текущая revision при `occurredAt >= activatedAt`; пропущенные старые события не воспроизводятся задним числом. Исторические версии правил и строгая доставка по конфигурации на момент события — отдельное расширение.

После изменения срока/этапа/lifecycle планировщик помечает потерявшие актуальность временные сообщения `resolvedAt`; они остаются в ленте, но больше не всплывают. Это включает переход `due_soon` в просрочку и выключение правила. Старые `readAt` не сбрасываются. После нового входа в этап меняется `enteredStageAt`, поэтому повторный простой может создать новое сообщение.

Для одной серверной установки MVP предусматривает один включённый экземпляр scheduler. При нескольких API-репликах запускать проверки только на одной через конфигурацию. Уникальный ключ защищает вставку от дублей, но не заменяет координацию курсоров и нагрузки. Если потребуется отказоустойчивое выполнение несколькими worker, добавить распределённую аренду либо очередь отдельным этапом.

### Доставка в приложение

Для MVP предлагается опрашивать уведомления через SWR каждые 2 минуты в активном окне, а также загружать их при открытии приложения, возвращении фокуса и восстановлении подключения. Polling реже одного раза в минуту согласован; 2 минуты — предлагаемое техническое значение. После ошибки — ограниченный backoff; не показывать новый error-toast на каждый неудачный poll. Не менять глобальное поведение fetcher: добавить локальный транспортный путь для фоновой ленты, если общий обработчик ошибок вызывает спам.

При предложенных интервалах задержка от наступления условия до показа может составлять примерно до 7 минут плюс время обработки и запросов при работающем сервере и активном окне. Строгого требования доставки в течение минуты нет; при простое, ошибках или неактивном окне задержка может быть больше.

Использовать `notification.open({ placement: 'bottomRight', ... })` через контекст Ant Design. Переопределить позицию только для бизнес-напоминаний, сохранив нынешнее расположение ошибок. Показать не более трёх всплывающих сообщений одновременно; накопившиеся объединить в «Есть N уведомлений» со ссылкой на ленту. Ant Design поддерживает контекстные вызовы и нужную позицию. [Документация Notification](https://ant.design/components/notification/).

`readAt` меняется явным действием «Прочитано» или переходом по ссылке; закрытие toast означает только скрытие. ID показанных сообщений сохранять локально с идентификатором установки/источника БД. Не использовать меняющийся loopback-порт как идентичность desktop-установки. При потере локального состояния допустим повторный показ непрочитанного сообщения, но новая запись в БД не создаётся. Между вкладками синхронизировать локальные ID через BroadcastChannel либо событие storage; строгая однократность показа между устройствами не обещается.

Лента MVP общая: прочтение в одном клиенте отражается во всех клиентах этой БД. Персональные получатели для MVP не нужны. Если они понадобятся после MVP, сначала вводятся пользователи и права доступа, затем отдельная таблица получателей/прочтений. Нельзя считать случайный `userId` из запроса авторизацией.

### Закрытое приложение

В web-варианте работающий сервер продолжает создавать уведомления при закрытом браузере. Для Electron согласовано: закрытое приложение не должно отправлять сообщения. При выходе останавливается и локальный сервер, cron в это время не работает. При следующем открытии создаются актуальные напоминания, а события из журнала обрабатываются по описанной политике; получение напоминаний после открытия допустимо.

Фоновую службу, режим работы после выхода и системную отправку уведомлений для закрытого Electron в рамках этой фичи не добавлять.

## 9. HTTP API

Все пути ниже имеют существующий префикс `/api`. Имена ориентировочные; при реализации сохраняется формат ошибок проекта и `WrapItemsInterceptor`. Списки возвращаются явно как `{ items, meta: { nextCursor, ... } }`, чтобы не получить повторную обёртку.

| Endpoint | Назначение |
| --- | --- |
| `GET/POST /production-boards` | Список и создание доски |
| `GET/PATCH /production-boards/:id` | Настройки, колонки, версия; PATCH с expectedVersion |
| `POST /production-boards/:id/stages` | Создание колонки |
| `PATCH /production-boards/:id/stages/:stageId` | Имя, цвет, архивирование, разрешённые настройки |
| `PUT /production-boards/:id/stage-order` | Полный список ID колонок и expectedVersion, без пропусков/дублей |
| `GET /production-boards/:id/cards?stageId=&cursor=&limit=` | Лёгкие карточки, счётчики отдельно, без позиций заказа |
| `POST /production-boards/:id/cards` | Назначить документ в начальную очередь |
| `POST /production-cards/:id/move` | Целевой этап, `beforeCardId?`, ожидаемые версии карточки/доски/группы |
| `POST /production-cards/:id/transfer` | Явный перенос на другую доску с ожидаемыми версиями обеих досок |
| `GET/POST /order-management/statuses`, `PATCH/DELETE /order-management/statuses/:id`, `POST /order-management/statuses/:id/archive` | Реализовано в OM-02: справочник custom status, scope и архивирование |
| `GET/PATCH /order-groups/:id/management` | Реализовано в OM-02: срок, custom status, lifecycle; PATCH с expectedVersion |
| `GET/PATCH /orders/:id/management` | Реализовано в OM-02: срок документа, effectiveDueDate, custom status; PATCH с expectedVersion |
| `GET /order-groups/:id/production` | Сводка этапов и прогресса всех документов |
| `GET /order-management/history?orderGroupId=&orderId=&offset=&limit=` | Реализовано в OM-02: история с offset/limit и meta.nextOffset |
| `GET/POST/PATCH /notification-rules[/:id]` | Настройка и отключение правил |
| `POST /notification-rules/preview` | Валидация, пример текста и ограниченный список совпадений, без отправки |
| `GET /notifications?cursor=&unreadOnly=&limit=` | Сохранённая лента |
| `PATCH /notifications/:id/read` | Идемпотентное прочтение |
| `GET/PATCH /order-management/settings` | Часовой пояс |

Перемещение в частично загруженной колонке задаётся соседним ID, а не индексом в видимой странице. Сервер проверяет, что сосед существует в целевой колонке; `null` означает конец всей колонки. Пагинация использует стабильную пару `(position, id)`; после перестановки клиент сбрасывает курсор колонки. У ленты — `(createdAt, id)`, после фокуса первая страница обновляется независимо от курсора старой истории.

## 10. Клиентская архитектура по FSD

Использовать существующие слои и public API `index.ts`. Не переносить весь SWR-код проекта ради фичи и не обобщать `useEntity` под доску.

| Размещение | Ответственность |
| --- | --- |
| `pages/production-board` | Страница доски, локальные DnD-состояния, редактор колонок, запросы и фильтры этой страницы |
| `pages/order` | Существующая страница: сводка производства, сроки группы и документов, история |
| `pages/order-management-settings` | Настройка custom status и правил, форма условий, предпросмотр |
| `pages/notifications` | Полная лента, фильтры, переходы и прочтение |
| `entities/order` | Дополнить уже существующую модель общими данными и отображением управленческого состояния |
| `entities/notification` | Общая модель уведомления и read-state для ленты и глобального показа |
| `features/change-order-management` | Общая форма срока/custom status, используемая на доске и странице заказа |
| `app/providers/OrderNotificationsProvider.tsx` | Подписка/polling и показ Ant Design; размещается внутри Router и AntApp |
| `shared/api` | Конкретные транспортные запросы и DTO новых ресурсов, через существующий fetcher/базовый URL |

Серверные данные хранятся в SWR. В Zustand не копировать доску и ленту целиком; локально держать только черновик настройки, выбранную карточку и состояние перетаскивания. После mutation обновлять связанные SWR-ключи доски, документа, группы и истории. Правила вычисления прогресса и уведомлений остаются на сервере.

Доска использует dnd-kit для колонок и карточек. Предусмотреть пустые колонки, DragOverlay, отдельную ручку перетаскивания, activation distance, клавиатуру и меню «Переместить в…» как доступную альтернативу. Не смешивать нажатие ссылки карточки с началом drag. Статические стили — Emotion; динамический transform от DnD допустим через `style`.

Переиспользуемую feature не импортировать из другой feature: их связывает страница. Не создавать отдельный entity-срез для каждой серверной таблицы; визуальный редактор доски пока используется только на одной странице и остаётся там.

Сведения ниже сверены с официальными источниками на дату документа. Версии из `package.json` — диапазоны существующих зависимостей, а не заявление о последней опубликованной версии. Точную версию новой зависимости зафиксировать lockfile при реализации после проверки peer dependencies NestJS 11.

Основной вариант использует Redis; актуальная документация также описывает PostgreSQL backend, но переносимость на SQLite это не решает. Для этого проекта сначала достаточно журнала в своей БД. [BullMQ](https://docs.bullmq.io/), [PostgreSQL backend](https://docs.bullmq.io/guide/postgresql) |
| Всплывающий UI | Существующий Ant Design | Уже есть контекст и оформление; отдельная toast-библиотека не нужна |
| Условия и шаблоны | DTO + небольшой типизированный evaluator и парсер токенов | Полноценные rules/template engines пока увеличат поверхность API без необходимости: задан ограниченный список событий, условий и переменных |
| Даты | Существующий клиентский dayjs; серверные календарные сравнения через Intl и строки дат | Не добавлять серверный dayjs только ради сравнения календарных дат; для будущих сложных расписаний пересмотреть выбор отдельно |

## 12. Миграция, проверка и внедрение

### Последовательность

1. Добавить nullable поля сроков/custom status, managementVersion, справочник и журнал. Сохранить существующий enum и текущие статусы всех заказов. Покрыть интеграцию переходов с ценовой логикой.
2. Добавить таблицы досок/карточек, команды с версиями, доску и сводку заказа. Можно предложить шаблон «Очередь → Раскрой → Покраска → Сборка → Готово», но создавать его по действию пользователя.
3. Добавить правила, scheduler, сохранённую ленту, безопасные токены и polling. Предлагать примеры правил выключенными: пользователь проверяет и включает их.
4. Проверить web/PostgreSQL и упакованный Electron/SQLite, восстановление после выключения, нагрузку и конкурентные действия. После этого включать фичу в обычную навигацию.

Не назначать существующие документы на этапы автоматически: `in_production` не содержит информации, на каком участке они находятся. Существующим заказам показывать «Производство не настроено» и действие назначения. Историю задним числом не выдумывать.

Для каждого изменения схемы сделать обе миграции. Проверить обновление существующих БД, включая старые завершённые заказы без карточек и пустые группы. Новые ограничения применяются к новым командам, а не требуют переписать старые данные при миграции.

Перед обновлением desktop сделать резервную копию SQLite; для web — штатный backup PostgreSQL. Первый релиз схемы аддитивный. При откате приложения новые данные сохранять; destructive down-миграция допустима только после отдельной оценки потери истории. Не менять production credentials или автоматически включать `synchronize`.

### Обязательные сценарии тестирования реализации

| Область | Что проверяем |
| --- | --- |
| Статусы | Custom status не меняет ценовую логику; одинаковые проверки нового и старого endpoint; terminal-заказ нельзя двигать без возобновления |
| Доска | Пустая колонка, перестановка, переход назад, перенос на другую доску, архивная/чужая колонка, копирование документа без карточки |
| Конкурентность | Два переноса одной версии: один успех, один 409; одновременная отмена группы и перенос; rollback истории; сетевой повтор не дублирует событие |
| Прогресс | Несколько документов, отсутствие карточки, пустой заказ, добавление документа, done и отмена, перестановка колонок не меняет проценты |
| Время | Граница полуночи, наследование срока, отсутствие срока, високосный день, переход DST в выбранной зоне, перенос срока, повторный вход в этап |
| Правила | AND/OR внутри наборов, scope группы/документа, выключение и revision, неизвестные переменные, попытка HTML/JS или внешней ссылки |
| Дедупликация | Два прохода дают одну запись; падение между вставкой и отметкой события откатывает оба действия; повтор после перезапуска; одна актуальная ежедневная запись после простоя |
| Доставка | Прочтение сохраняется, закрытие toast не читает, старые записи доступны, восстановление сети, несколько вкладок, удалённый документ, обе схемы Router; закрытый Electron не отправляет сообщения, после открытия появляются актуальные напоминания |
| БД | Миграции и интеграционные проверки FK/unique/транзакций на PostgreSQL и SQLite; отсутствие зависимости от PostgreSQL-only SQL |

Для реализации использовать существующие Jest/Vitest и MSW. Запускать релевантные тесты, клиентский `npm run coverage`, серверный `npm run test:cov -- --runInBand`, e2e для БД и сборки обоих пакетов. Команды с coverage здесь — план проверки будущего кода; в документационной задаче тесты приложения не запускались.

Целевые проверки производительности на тестовом наборе: 10 000 документов, 100 правил, до 200 загруженных карточек на странице. Проход scheduler должен укладываться в выбранный интервал проверки (предлагается 5 минут), запрос страницы доски — ориентировочно до 500 мс на согласованном окружении. Это критерии для измерения, а не текущие замеры. При превышении сначала проверить выборки, индексы и пагинацию, затем решать вопрос worker/очереди.

Логировать время последнего успешного прохода, длительность, число проверенных объектов/созданных записей/дублей/ошибок и возраст старейшего необработанного события. Не писать содержимое заказов в технические логи без необходимости. В настройках показывать последнее успешное выполнение, чтобы остановившийся scheduler был заметен.

## 13. Согласованные решения MVP

По ответам пользователя зафиксированы следующие границы реализации:

1. **Карточка — документ с одним текущим этапом.** Этого достаточно для производства в рамках MVP.
2. **Прогресс — оценка по этапам и невзвешенное среднее по документам.** Количественный учёт изготовления в MVP не требуется.
3. **Срок — календарная дата без времени суток, по умолчанию в `Europe/Moscow`.** Для MVP этого достаточно; учёт рабочих и выходных дней остаётся возможным расширением.
4. **Уведомления общие для установки, персональные получатели не нужны.** Допустимы задержки больше минуты и клиентский polling с интервалом больше минуты. Техническое предложение: серверная проверка раз в 5 минут, клиентский polling раз в 2 минуты.
5. **Закрытое приложение Electron не отправляет сообщения.** Актуальные напоминания поступают после открытия; постоянная фоновая работа не требуется.
6. **Заказ закрывается явно.** Допускается закрытие без полного производственного учёта с указанием причины.

Документ можно использовать как основу декомпозиции MVP с указанными границами. Точные интервалы проверки и polling предложены для реализации и могут быть уточнены без изменения согласованных продуктовых требований.
